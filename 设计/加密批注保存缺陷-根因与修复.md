# 加密 PDF 批注保存缺陷：根因与修复

> 日期：2026-10-11
> 触发：为核实「PyMuPDF 产出的 `/Encrypt` 写成直接字典」这一偏差而做的校验
> 结论：**原偏差无需处理（无实际影响）；但同一轮校验挖出一个严重缺陷——给加密 PDF 保存批注会摧毁页面内容，已定位根因并修复。**
> 状态：修复已落地（`backend/engine.py` 2 处 + `tests/test_engine.py` 1 处断言），引擎全量测试与 qpdf 严格校验通过

---

## 1 结论摘要

| 项 | 结论 |
|---|---|
| **缺陷** | 对**已加密**的 PDF 做批注就地保存后，产物**所有页的原始内容丢失**（仅注释本身可见）：实测 3 页文档中第 2、3 页渲染全白（非白像素 0），第 1 页文本从 109 字符降到 4 字符（只剩笔记文字） |
| **严重度** | 高。就地保存会**覆盖源文件**，用户没有第二次机会 |
| **影响面** | 仅「加密 PDF + 批注保存」路径；未加密文档的批注保存、以及「解密另存」路径均正常 |
| **根因** | `_atomic_save_in_place` 在**认证之后**读取 `doc.needs_pass`，触发 PyMuPDF 1.28.2 的 AES 状态缺陷，毒化紧随其后的加密保存 |
| **修复** | 改用 `open_pdf` 在**认证前**捕获的快照 `_aipdf_needs_pass`；语义等价，一行级改动 |
| **验证** | 真实引擎 CLI 子进程产物 `qpdf --check` **EXIT=0**（修复前 EXIT=2/3）；引擎全量 45 项 `errors=2 / skipped=2` 与既有基线一致；新增内容完整性断言在修复前文件上**确实失败**（检测到空白页 2、3） |
| **原问题** | PyMuPDF 把 trailer 的 `/Encrypt` 写成**直接字典**（pypdf / KillerPdf 写间接引用）——qpdf 接受、PDFium / pypdf / pdfminer 均可正常读取。**建议记录为已知偏差，不做规范化** |

## 2 证据链（可复现）

### 2.1 最小复现

合成 3 页、每页有可辨识文本的 AES-256 加密 PDF（`user_pw=test123`），用**真实引擎 CLI 子进程**调一次批注保存：

```json
{"operation":"save_annotations","files":["<encrypted-3p.pdf>"],
 "options":{"password":"test123","annotations":[
   {"action":"add","id":"h","kind":"highlight","page":0,"rect":[50,100,300,130]},
   {"action":"add","id":"n","kind":"note","page":0,"rect":[50,300,300,360],"text":"审计笔记"}]}}
```

引擎返回 `{"ok": true, ...}`（**静默成功**），但产物：

| 检查 | 保存前 | 保存后（修复前） |
|---|---|---|
| page 0 文本 / 非白像素 | 109 字符 / 6469 px | **4 字符** / 29728 px |
| page 1 文本 / 非白像素 | 109 字符 / 6515 px | **0 字符 / 0 px（全白）** |
| page 2 文本 / 非白像素 | 109 字符 / 6522 px | **0 字符 / 0 px（全白）** |
| `qpdf --check --password=test123` | — | **EXIT=2**：`error decoding stream data for object 9 0: stream inflate: incorrect header check`、`page 2: content stream: errors while decoding content stream` |
| MuPDF 自身诊断 | — | `syntax error in syntax error in content stream` ×14 |

产物结构层面：`obj 6` 声明 `/Length 32` 而 `stream` 与 `endstream` 之间**实际 0 字节**（空流）。

### 2.2 为什么既有测试没抓到

`tests/test_engine.py::test_encrypted_annotation_save_preserves_encryption` 原断言只有：仍加密、原用户密码可解、**页数 == 3**、`/Encrypt` 指纹不变、注释数与内容正确。
**页数不变而页面内容全丢**，所以用例一直是绿的。

## 3 根因定位（对照实验）

在**完全隔离的进程**中逐项对照（每次只改一个变量，产物一律由新进程校验，避免 MuPDF 进程级 AES 状态污染测量）：

| 变量 | 结果 |
|---|---|
| 引擎原路径（`save_annotations_request`） | **BROKEN**（页 2/3 全白） |
| 逐行内联复刻 `_atomic_save_in_place` 函数体 | OK |
| 逐字复制函数体（含 `if doc.needs_pass and not password:`） | **BROKEN** |
| 内联副本 + 仅追加 `_ = doc.needs_pass` | **BROKEN** |
| 内联副本 + `_ = doc.is_encrypted` | OK |
| 内联副本 + `_ = doc.page_count` | OK |
| 内联副本 + `_ = doc.permissions` | OK |
| 内联副本 + `_ = doc.metadata` | OK |
| 内联副本 + `_ = doc[0].number` | OK |
| 去掉 `needs_pass` 读取（用认证前快照） | **OK** |

**结论：触发条件唯一且精确——在已认证的 AES 文档上读取 `doc.needs_pass`，随后做加密保存。**
（认证**前**读 `needs_pass` 安全：`open_pdf` 本身就是这么用的，且该路径正常。）

### 3.1 影响面界定

| 场景 | 是否受影响 |
|---|---|
| 加密 PDF + 批注就地保存（加密重写） | ❌ **受影响**（本缺陷） |
| 未加密 PDF + 批注就地保存 | ✅ 正常 |
| 加密 PDF + 解密另存（`PDF_ENCRYPT_NONE`） | ✅ 正常（实测对照） |
| 普通工具输出（`save_pdf` 强制 `PDF_ENCRYPT_NONE`） | ✅ 正常 |

`needs_pass` 在引擎内共 8 处引用；除本次修复的 1 处外，其余均在**认证前**读取（`open_pdf` 的两处）或作用于**另一个文档句柄**（`_validate_saved_temp` 的 temp、protect 的输出校验、compress 的分支判断），不受影响。`_doc_is_encrypted` 的回退分支也读 `needs_pass`，但生产路径恒有 `open_pdf` 的快照，已在代码注释中标注风险。

## 4 修复

### 4.1 `backend/engine.py` — 认证前捕获快照

```python
    doc._aipdf_encrypted = bool(doc.is_encrypted or doc.needs_pass)
    # 认证前捕获「是否需要密码」：认证后在 AES 文档上再读 needs_pass 会破坏随后的
    # 加密保存（见 _atomic_save_in_place 的说明），故一律用这里的快照。
    doc._aipdf_needs_pass = bool(doc.needs_pass)
```

### 4.2 `backend/engine.py` — 保存路径不再读 `needs_pass`

```python
    if encrypted:
        # 【禁止在此读 doc.needs_pass】...（完整说明见代码注释）
        if getattr(doc, "_aipdf_needs_pass", False) and not password:
            raise UserError("加密文档需要密码才能保存批注。")
```

**语义等价性**：原判断 `doc.needs_pass and not password` 在认证后求值；新判断用认证前快照。
- 有真实用户密码的文档：认证前 `needs_pass=True`，认证后传入了 password → 两者都不抛。
- 空用户密码（仅 owner 密码）文档：认证前 `needs_pass=False` → 两者都不抛。
- 需要密码但未提供：`open_pdf` 阶段已提前抛错，到不了这里。

### 4.3 `tests/test_engine.py` — 补内容完整性断言

在 `test_encrypted_annotation_save_preserves_encryption` 内，对每一页断言**渲染非空白**：

```python
            for index,page in enumerate(d):
                gray=page.get_pixmap(dpi=36,colorspace=fitz.csGRAY)
                self.assertLess(min(gray.samples),250,f"第 {index+1} 页渲染为空白（内容流被写坏）")
```

用渲染而非 `get_text()`：加密文档上 MuPDF 读字符串本身不可靠（见 `learnings.md`）。

## 6 原问题的回答：`/Encrypt` 直接字典要不要规范化

| 项 | 实测 |
|---|---|
| PyMuPDF 产物 | trailer `/Encrypt<</Filter/Standard/R 6/V 5/...` → **直接字典**（本缺陷修复前后均如此） |
| pypdf 产物 | `/Encrypt 8 0 R` → 间接引用 |
| KillerPdf 产物 | 间接引用 |
| `qpdf --check` | **不就此报警**（EXIT=0/3 与 `/Encrypt` 形态无关） |
| PDFium（本项目渲染栈 155，经 pypdfium2） | 正常打开 |
| pypdf / pdfminer | 正常打开与解密 |
| KillerPdf.Engine | **拒绝**：`InvalidOperationException: The trailer /Encrypt value is not indirect.` |

**结论：记录为已知偏差，不做规范化。** 理由：主流读取方（qpdf、PDFium、pypdf、pdfminer、Adobe/Chrome 一类宽容实现）均接受；唯一拒绝者是 KillerPdf.Engine，而该引擎已因其他原因不采纳（见 `阅读器复用评估-GitHub现成方案.md` 第 7 节）。规范化为间接引用需要引入第三方重写（pypdf/pikepdf），会改动现有加密保存链路并带来新的回归面，收益不足。

> 注：ISO 32000-1 为付费标准，本报告未读到原始条款，仅依据 pypdf 与 KillerPdf 的实现惯例表述为「偏离惯例」，未断言「违反规范」。建议向 PyMuPDF 上游反馈，由上游决定是否调整。
