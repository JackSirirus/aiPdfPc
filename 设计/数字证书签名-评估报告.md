## 0. 结论摘要

| 问题 | 结论 |
| --- | --- |
| 引擎（PyMuPDF 1.28.2）能**生成**数字签名吗？ | **不能**。`Document.save()` 无 `sign` 参数，无 `set_sigflags`，无任何签名写入 API |
| 引擎能**创建签名字段**吗？ | **能**。`Page.add_widget(PDF_WIDGET_TYPE_SIGNATURE)` 实测写出 `/FT /Sig` + `/T`，但 `/V` 为空（未签名） |
| 引擎能**验证**签名吗？ | **几乎不能**。仅 `Document.get_sigflags()`，且实测该值**不可作为「是否已签名」的判据** |
| .NET 侧有现成落点吗？ | **有，且零依赖**。`SignedCms` / `CmsSigner` / `Rfc3161TimestampRequest` 位于 WindowsDesktop 共享框架，**实测无需 `PackageReference` 即可编译** |
| 建议 | **条件式 Go**（先做架构决策）；**当前状态下 No-go**——理由见 §4，不是成本问题而是**与既有保存契约冲突** |

## 2. 技术路径核实（全部为本次实测，非推测）

### 2.1 引擎侧：只能建字段，不能签名

```
PyMuPDF 1.28.2
  Document.save() 参数: [..., encryption, permissions, owner_pw, user_pw, ...]   ← 无 sign
  Document 签名相关成员: ['get_sigflags']
  has set_sigflags: False      has Annot.set_signature: False
  add_widget(PDF_WIDGET_TYPE_SIGNATURE) → OK（写出 /FT /Sig、/T Signature1）
  该文件 get_sigflags() = 3，但 /V = null（未签名），无 /Sig 对象
```

两点必须记住：

1. **`get_sigflags()` ≠ 已签名**。实测只有**空签名字段**时它也返回 `3`（SigFlags 的
   `SignaturesExist | AppendOnly` 位被 MuPDF 置上）。判「是否已签名」应看字段的 **`/V`**（签名值字典）。
2. 引擎有 `xref_set_key`（低层写对象）与 `save(incremental=True)`，因此**理论上**可以手写
   `/Sig` 字段对象；但**签名值本身**（CMS + ByteRange）不是引擎能算的。

### 2.2 .NET 侧：零依赖可用（重要成本发现）

```
ref 包:  .../packs/Microsoft.WindowsDesktop.App.Ref/8.0.30/ref/net8.0/System.Security.Cryptography.Pkcs.dll
共享框架: .../shared/Microsoft.WindowsDesktop.App/8.0.30/System.Security.Cryptography.Pkcs.dll
NuGet 缓存: 无 system.security.cryptography.pkcs 包
```

用探针文件（`SignedCms` + `CmsSigner` + `CertificateRequest` + `Rfc3161TimestampRequest`）
在**本项目** `net8.0-windows` + `UseWPF` 下编译：**通过，0 个错误，且未添加任何 `PackageReference`**。

→ 签名与时间戳的密码学原语**不需要新增依赖、不需要联网还原**，与仓库「不下载模型/字体」的纪律不冲突。
（对比：`System.Speech` 需要 NuGet 包与首次联网还原，见 T8。）

### 2.3 `/Sig` + `/ByteRange` + `/Contents` 的写入路径

PDF 签名的结构要求决定了实现方式：

1. 文件里要有**签名字段**（`/FT /Sig`），其 `/V` 指向签名值字典；
2. 签名值字典含 `/ByteRange [0 a b c]`（把 `/Contents` 本身挖空的两段字节范围）与
   `/Contents <固定长度十六进制占位>`；
3. 计算哈希时必须**恰好**覆盖 ByteRange 指明的字节。

因此必须是**两遍写入**：先写含定长占位符的文件 → 算出 ByteRange → 对字节做哈希并生成 CMS →
**原地回填** `/Contents`（长度不变）。且必须是**增量更新（append-only）**：直接重写整个文件会
使已有签名失效。

可选落点（按可控性排序）：

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| **A. 引擎建字段 + C# 后处理签名** | 引擎用 `add_widget` 建空签名字段并保存；C# 读字节、算 ByteRange、`SignedCms` 生成、原地回填 | **推荐**。职责清晰：引擎不碰密码学，C# 不碰 PDF 结构 |
| B. C# 全包 | C# 直接构造 `/Sig` 字段对象并写增量更新 | 需要自写 PDF 对象语法，风险高 |
| C. 引第三方 PDF 签名库 | 如 iText（AGPL/商业双许可）等 | **不建议**：许可证与体积成本高，且违背「最小依赖」 |

### 2.4 时间戳（RFC 3161）

`Rfc3161TimestampRequest` / `Rfc3161TimestampToken` 可用，但**必须联网访问 TSA 服务**。
按仓库纪律，这属于「隐式上传」范畴，因此：

- 默认**不启用**；
- 启用须**用户显式配置 TSA 地址并明确同意**（与云端翻译同一条纪律）；
- 未配置时签名仍有效，只是**无第三方可信时间**（与 Acrobat 的默认行为一致）。

### 2.5 证书来源

| 来源 | 说明 |
| --- | --- |
| Windows 证书存储（`X509Store(StoreName.My)`） | 用户已安装的个人证书；配合 `X509Certificate2UI` 选择器，私钥不出本机 |
| 硬件令牌 / 智能卡（CNG） | 签名在硬件内完成，安全性最高；`SignedCms` 支持 CNG 密钥 |
| 自签名证书 | 仅适合内部/演示；对外必须标注「未受信任」 |

**不做**：生成证书、代管私钥、上传证书或文档到任何服务。

## 3. 与「手写签名」工具的边界

现有工具（`backend/catalog.py`）已带正确声明：

> `sign` /「PDF 签名」/「手写、输入姓名或放置签名图片」
> note：**「在签名板上书写，然后在预览中框选位置。属于可视签名，不是证书数字签名或远程签署服务。」**

对比报告的风险行已明确：

> **用图片签名冒充电子签名** — WPS 官方文章自认「图片签名不包含加密认证信息」——我们的
> 「PDF 签名」工具同样是手写/图片签名，**对外不能称「电子签名」**。

### 3.1 对外表述规则（建议固化为可检查的规则）

1. **手写/图片签名**只能称「**手写签名**」「可视签名」「签名图片」，**禁止**称「电子签名」
   「数字签名」「电子签章」「具有法律效力」。
2. 二者的区别必须**在界面上可见**，不能只在文档里：签名工具页与结果提示都要有
   「这不是证书数字签名」的说明。
3. 若将来实现了数字证书签名，它必须是**独立入口**（如「数字签名（证书）」），
   不得与「手写签名」共用名称或图标，避免用户误认。
4. 任何「已签名」提示都必须说明**签名主体**（证书 CN/颁发者）与**是否受信任**；
   自签名证书必须显式标注「未受信任」。
5. 不宣称法律效力（不同法域要求不同，且需可信时间戳与长期验证材料）。

### 3.2 可加的机械防线（若决定实现）

- 文案审计：像 `ThemeManagerTests.XamlAudit_*` 那样加一条**字符串审计测试**，扫描 UI 资源与
  catalog 描述里「电子签名/数字签名」字样是否只出现在证书签名相关位置；
- 目录描述回归：`catalog.py` 的 `sign` 条目 note 已含边界声明，加测试防被改写掉。

## 4. ⚠️ 与现有架构的**硬冲突**（本报告最重要的发现）

本应用当前的批注保存链路是：**就地原子替换源文件**（`save_annotations` → 引擎写回 → 宿主
close-first 重载），并带加密文档的增量写回。这与数字签名**根本冲突**：

1. **签名覆盖的是字节范围**。签名之后**任何**字节修改（哪怕只加一条批注）都会让签名失效。
2. 因此「已签名文档」必须对**就地保存**变成**只读**——否则用户会在不知情的情况下毁掉签名。
   这需要改动保存链路的状态机（`AnnotationSaveSession` 的只读判定、savepill 的失败/另存为路径、
   关闭前 flush 决策），而**不是**在签名功能里加几行。
3. 加密 + 签名叠加、增量更新与「原子替换」的语义冲突，都需要单独设计（例如签名后只允许
   「另存为」到新文件，原文件保持已签名状态不变）。
4. 已有的 T0a 教训（加密文档 `needs_pass` 快照）说明：**在写回路径上做实验的代价很高**，
   回归面覆盖加密、批注、冲突检测、close-first 重载四条链路。

→ **建议的架构前置决策**（做签名之前必须先拍板）：

> 「签名后的文档在本应用中是否允许继续批注保存？」
> - 选 **A：签名后只读**（推荐）——签名入口在保存/另存为流程里，签名成功后文档转为只读，
>   批注改动只能「另存为」新文件。
> - 选 B：签名后仍可改 —— 必须实现「签名失效检测 + 明确告知 + 二次确认」，成本与风险都显著更高。

## 5. 工作量区间

| 范围 | 内容 | 估时 |
| --- | --- | --- |
| **最小可用（MVP）** | 本机证书选择 + 单个签名字段 + 两遍写入 + 原地回填 + 签名后只读（架构 A） | **3–5 天** |
| + 验证 | 打开时显示签名状态（有无 `/V`、证书主体、是否受信任、文档是否被改过） | +2–3 天 |
| + 时间戳 | TSA 显式配置与同意流程、RFC 3161 请求/回填 | +1–2 天 |
| + 对外可见签名外观 | 签名字段的可视化外观（姓名/日期/原因/位置） | +1–2 天 |
| 专业级（**不建议**） | 认证签名（certify）、多人会签、CAdES、LTV/OCSP 嵌入、长期验证 | 数周 |

对比报告原估「1 周+」，与本评估一致；**MVP 的 3–5 天不包含 §4 的架构改造**，
若只做 MVP 且不解决只读问题，等于交付一个会毁掉用户签名的功能——所以那 3–5 天必须叠加架构决策的工时。

## 6. go / no-go 建议

**Go 的前提（全部满足才建议做）**

1. 拍板 §4 的架构决策（推荐「签名后只读」）；
2. 接受「MVP 不含时间戳」的对外表述（不得宣称可信时间与法律效力）；
3. 有真实证书可用于验收（自签名证书只能验证流程，不能验证信任链 UI）。

**当前建议：No-go（暂不实现）**

理由不是成本，而是**优先级与风险不对称**：

- 本项目的差异化优势是「33 个免费本地工具 + 整篇翻译 + 无遥测」；数字证书签名是**专业低频**能力，
  4/6 家竞品有，但目标用户里需要它的人群很窄；
- 它**必须**先改保存链路（§4），而保存链路是本项目最敏感、回归面最大的部分（加密/批注/冲突/重载）；
- 一旦做了，**签名后只读**会削弱本应用「随时批注」的核心体验——这是一次产品取向的取舍，不是技术题。

**若决定做**，建议顺序：

1. 先落地 §4 的只读状态机改造（**可独立提交、独立验证**，即使不做签名也有价值：为「只读文档」提供正确语义）；
2. 再做 MVP 签名（本机证书 + 两遍写入）；
3. 最后才考虑验证与时间戳。

## 7. 本次评估的验证方式（诚实标注）

| 项 | 方式 | 结果 |
| --- | --- | --- |
| PyMuPDF 能否签名 | 直接 introspect `save()` 参数、`Document`/`Annot` 成员、`set_sigflags` | 不能（无相关 API） |
| PyMuPDF 能否建签名字段 | 实际创建 `PDF_WIDGET_TYPE_SIGNATURE` widget 并保存，再低层读 `/FT`、`/V`、`get_sigflags` | 能建字段，`/V` 为空；`get_sigflags()=3` |
| .NET PKCS#7 是否可用 | 在本项目 `net8.0-windows` + `UseWPF` 下编译探针文件（`SignedCms`/`CmsSigner`/`Rfc3161TimestampRequest`） | 编译通过，**0 个 PackageReference** |
| 与保存链路的冲突 | 阅读既有 `save_annotations` 就地写回 + close-first 重载实现 | 冲突成立（§4） |
