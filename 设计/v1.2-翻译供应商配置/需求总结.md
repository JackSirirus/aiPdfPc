## 背景

v1.1 已正式交付 AI PDF 翻译能力（划词 / 整篇 / 批量），默认本地引擎，可选云端 LLM。云端配置当前存放在**设置 → 翻译**页面（`SettingsDialog.cs`），用户需手动填写端点地址、模型名、API Key。当前范围为 33 个工具。

v1.1 的供应商配置存在两个层面的问题：

**体验问题——配置门槛过高。** 用户必须知道具体的服务商端点地址和模型名才能配置云端翻译。没有预设列表、没有模型拉取、没有引导。设置页面的提供商编辑器是一组自由文本字段（ComboBox 选已有 / ＋新增 → 填 identifier → 填 endpoint → 填 model → 填 key → 保存），没有任何内置供应商的概念。这与 opencode CLI 的体验形成鲜明对比——后者有 `models.dev` catalog、预置 provider 列表、一键选择模型。

**功能缺陷——Engine 单选按钮从未生效。** 翻译面板（整篇 Tab / 批量工具页）中的「本地 / 云端 LLM」单选按钮（`TranslationConfigViewModel.Engine`）是**只写不读**的：XAML 双向绑定到 `IsLocalEngine` / `IsCloudEngine`，`MainWindow.xaml.cs:1005` 还会在弹窗后重置为 `TranslationEngineKind.Local`——但运行时**从不读取**该值。实际的本地/云端目的地由 `SettingsTranslationRuntimeConfigProvider.Resolve()` 硬编码规则决定：优先取名为 `"local"` 的 provider（必须 loopback），否则取第一个已保存的云端 provider。换言之，用户在面板上选「云端 LLM」并不会真的切换到云端；用户在面板上选「本地」也不会阻止使用云端。**面板与运行时之间存在割裂。**

此外，设置页面的供应商编辑器只存在于 `SettingsDialog.cs`（code-built WPF，无 XAML）；翻译面板（`TranslationConfigPanel.xaml`）内没有任何供应商/密钥/模型选择控件。用户必须跳到设置页才能切换服务商。

本文件是 `/design-exploration` 第一~四步成果的落盘总结。v1.2 的目标是：**统合「供应商」概念、修复 Engine 割裂、降低配置门槛、并在面板内提供快捷切换。**

## 目标

1. **供应商预设**：内置 14 家主流云端服务商 + 自定义入口，用户选名字即自动填充端点和默认模型，不再需要手查手填。
2. **本地服务简化**：本地模式只需填 OpenAI-compatible base URL（提供常用端口建议），一键拉取可用模型列表，选模型即可。
3. **面板快捷切换**：翻译面板内内联展开供应商快捷切换（非模态、非跳转设置页），在上下文中即可更换目的地。
4. **修复 Engine 割裂**：让面板的供应商选择**真正驱动**运行时目的地——消除「选了不生效」的割裂。
5. **凭据安全不变**：API Key 仍仅通过 Windows Credential Manager 存储、仅经 stdin 传递，密钥不进 argv / 日志 / 环境变量 / 崩溃转储 / 配置文件。
6. **视觉复用 v1.1 A+C 暖纸体系**，**不新增主题 token**。

## 功能范围

### 做什么（V1.2 纳入）

- **内置供应商预设表**：14 家预置服务商（OpenAI / Anthropic Claude / Google Gemini / DeepSeek / 阿里通义千问 / 智谱 GLM / 月之暗面 Kimi / Groq / MiniMax / Doubao 豆包 / opencode Zen / opencode go / GLM Coding Plan / Kimi Code），每条包含 provider id、显示名、base URL、环境变量名、默认模型。
- **云端供应商配置（设置页重构）**：Master-detail 双栏布局——左侧分组供应商列表（内置 + 自定义），右侧配置详情（端点 / 模型 / Key / 同意状态 / 操作按钮）。
- **本地服务配置（设置页）**：OpenAI-compatible base URL 输入 + 端口建议下拉 + 「拉取模型」按钮（调 `GET {base}/v1/models`）+ 模型选择。
- **自定义供应商**：保留自由文本入口（任意 base URL + 模型名），兼容非预置服务商。
- **面板内联快捷切换**：整篇 Tab / 批量工具页的配置区域内，内联展开供应商选择器（展开态显示 provider 列表 + 模型选择 + 当前 key 状态），**不是模态弹窗，不是跳转设置页**。
- **修复 Engine 割裂**：面板的供应商选择器直接驱动 `SettingsTranslationRuntimeConfigProvider` 的目的地决定，消除 `TranslationConfigViewModel.Engine` 只写不读的问题。
- **模型列表拉取**：本地和云端均支持拉取模型列表（云端部分供应商支持）。拉取失败时给出明确错误提示并允许手动输入。
- **URL 智能处理**：自动补全 `https://` 前缀、处理尾部斜杠、识别 `/v1` 路径（避免重复拼接）、处理 `localhost` vs `127.0.0.1` 一致性、识别用户粘贴的完整 `/v1/chat/completions` URL 并截取到 base。
- **凭据与同意复用**：沿用 v1.1 的凭据存储（Windows Credential Manager）与同意绑定（`provider + endpoint-origin + key-fingerprint`，180 天 TTL）机制，**不改变安全边界**。
- **供应商「测试连接」与「拉取模型」**：用户显式触发的连通性/凭据验证（见下方安全规则）。

### 不做什么（V1.2 明确排除）

- **Ollama 原生协议**：不做 Ollama `/api/tags` 或 `/api/generate` 对接，仅支持 OpenAI-compatible `/v1/models` 端点。
- **自动探测/检测本地运行时**：不做端口扫描、不做服务发现；用户必须显式填写地址。
- **新主题 token**：复用 v1.1 A+C 暖纸体系，不新增 Brush / 色值。
- **密钥轮换/多 Key 管理**：每个 provider + endpoint 组合只存一个 key；不做多 key 池或自动轮换。
- **供应商排序/自定义分组**：内置列表固定顺序；自定义 provider 追加到列表末尾。
- **翻译质量调优**：不改 prompt / 不改分块策略 / 不改回填排版；本版本仅改「目的地从哪来」。

## 载体

v1.2 不新增界面容器，完全复用 v1.1 的载体结构，在现有触点上增强：

| 触点 | v1.1 现状 | v1.2 变更 |
|---|---|---|
| 设置页 → 翻译 | `SettingsDialog.cs` code-built，自由文本编辑器 | 重构为 master-detail 双栏（左侧供应商列表，右侧配置详情） |
| 整篇 Tab 配置区 | `TranslationConfigPanel.xaml`，含 Engine 本地/云端 radio | 新增内联供应商快捷切换（替代或包裹原 Engine radio 区域） |
| 批量工具页配置区 | 复用 `TranslationConfigPanel.xaml` | 同整篇，自动继承 |
| 划词 Tab | `SelectionTranslationCard.xaml`，只读显示 EngineLabel/RouteLabel | 显示当前生效的供应商名（只读，不提供切换入口） |
| 首次云端同意模态 | F5 流程 | 不变；同意绑定 `provider + endpoint + key-fingerprint` |

### 关键交互：面板内联快捷切换

- **触发**：配置区顶部显示当前生效的供应商名 + 「切换」链接。
- **展开**：点击后在原位展开（accordion 式），显示：供应商下拉（内置 + 自定义 + 本地）→ 选云端时显示模型下拉 → 选本地时显示 base URL + 端口建议 + 拉取模型按钮。展开不遮挡其他配置项，不弹模态。
- **收起**：选择完成后自动收起，或点击「收起」。收起后顶部显示新选中的供应商名。
- **与设置页的关系**：面板快捷切换是设置页的**快捷入口**——面板内的选择会同步到设置页的 provider 列表（如果该 provider 尚未保存则自动创建）；设置页的修改也会反映到面板。

## 关键决策（已锁定）

| # | 决策 | 原因 / 约束 |
|---|------|------|
| 1 | **范围 = 云端 + 本地一起做** | 云端和本地的供应商配置本质上是同一数据模型的两种形态（base URL + model + optional key）；拆开做会导致两次重构 |
| 2 | **内置供应商 = 14 家**（OpenAI / Anthropic Claude / Google Gemini / DeepSeek / 阿里通义千问 / 智谱 GLM / 月之暗面 Kimi / Groq / MiniMax / Doubao 豆包 / opencode Zen / opencode go / GLM Coding Plan / Kimi Code） | 覆盖主流中英文 LLM 服务商 + 订阅网关 + 编程套餐；维护者确认 |
| 3 | **本地 = OpenAI-compatible base URL only**；不做 Ollama 原生协议；不做自动探测 | 所有主流本地推理框架（Ollama / LM Studio / vLLM / llama.cpp）均已支持 OpenAI-compatible `/v1` 端点；自动探测增加复杂度但收益有限 |
| 4 | **自定义供应商保留** | 兼容企业内网、私有部署、新服务商；自由文本入口不删 |
| 5 | **设置页布局 = master-detail 双栏**（左列表右详情） | 供应商数量多（14 家内置预设 + N 自定义 + 本地），列表 + 详情是成熟的多条目管理模式 |
| 6 | **面板入口 = 内联展开**（非模态、非跳转设置页） | 翻译场景中切换供应商是高频操作（试不同模型/服务商），打断上下文的成本高 |

| 8 | **本地 UX = 端口建议下拉 + 一键拉取模型** | 端口建议降低记忆负担；拉取模型是必要的（模型名必须显式选择） |
| 9 | **修复 Engine-radio/destination 割裂**：面板选择驱动 `SettingsTranslationRuntimeConfigProvider`，消除只写不读 | 这是一个实际影响用户的 bug；面板声称选了本地但可能用云端（或反之），导致非预期的 API 调用与费用 |
| 10 | **安全不变不变**：API Key 仅存 Windows Credential Manager；仅经 stdin 传递；同意按 `provider + endpoint-origin + key-fingerprint` 绑定，180 天 TTL；云端要求 HTTPS（loopback 可用 HTTP） | 沿用 v1.1 安全约定（详见 `../v1.1-翻译/需求总结.md` §云端配置复用与同意） |
| 11 | **新增 `apiProtocol` 维度**（`openai` \| `anthropic`），provider 级；支持**按模型覆盖**（`modelProtocols`） | 以支持 opencode go 等混合协议供应商——同一 provider 下不同模型可能使用不同协议 |
| 12 | **Anthropic 协议适配在 Python 引擎侧统一实现**（`backend/translate/llm.py` 增加 `/v1/messages` 分支、`x-api-key` / `Authorization: Bearer` 两种凭据形式、`anthropic-version` 头） | 此决定同时解决原「未决项 #1」（Anthropic Claude 适配）；引擎侧统一处理避免 C# / Python 双重适配 |
| 13 | **内置预设由 11 家扩为 14 家**，新增 `opencode-go`、`glm-coding-plan`、`kimi-code` | 覆盖订阅网关与编程套餐两种新型态；编程套餐端点标注合规约束（见 §编程套餐合规约束） |
| 14 | **编程套餐端点默认不选**，标准 API 为默认；选中套餐端点时展示常驻合规警示，并提供「改用标准 API」一键切换 | GLM / Kimi 官方 FAQ 明确限制编程套餐仅供官方支持工具使用，自建应用调用可能不计入额度 |

## 技术约束与研究结论

### 当前数据模型

`TranslationProviderConfig`（`TranslationProviderConfig.cs`）的字段：

```
provider  : string   — 供应商标识（"local" / "deepseek" / 自定义名）
endpoint  : string   — 端点 URL（base URL）
model     : string   — 模型名（用户必须选择）
```

不存 API Key（Key 在 Windows Credential Manager 中，地址 = `AIPDF-Translate-{provider}-{sha256(origin)[:16]}`）。`ValidationError` 为 `[JsonIgnore]`，仅运行时校验用。

### 当前运行时选择逻辑

`SettingsTranslationRuntimeConfigProvider.Resolve()`（`SettingsTranslationRuntimeConfigProvider.cs:45-97`）硬编码规则：

1. 加载 `AppSettings.TranslationProviders`，过滤 `IsUsable` 条目。
2. 若存在名为 `"local"` 的 provider → 必须是 loopback 地址（`127.0.0.1` / `::1` / `localhost`），否则返回 `NotLoopback` 错误。
3. 若无本地 → 取第一个云端 provider → 检查凭据（`NoCredential`）→ 检查同意（`NoConsent`）。
4. 无 provider → `NoProvider`，提示去设置页添加。

**注意：`TranslationConfigViewModel.Engine` 的值完全不参与上述决策。** `FullTranslationViewModel.Start`（lines 400-456）和 `TranslationBatchViewModel` 调用 `_configProvider.Resolve()` 时从不传入 Engine 标志。`MainWindow.xaml.cs:1005` 仅在同意弹窗后单向重置 `Config.Engine = TranslationEngineKind.Local`，但这也是只写不读。

### `TranslationEngineOptions.Build` — 终点组装

`FullTranslation.cs:96-148`，`Build` 方法将 `endpoint` / `model` / `apiKey`（从 stdin 传入）合并为 `Dictionary<string, object?>`，**不包含 provider name**。Python 引擎只看到 endpoint + model + key，不知道是哪家服务商。

### 凭据存储

- 目标名格式：`AIPDF-Translate-{provider}-{sha256(NormalizeEndpoint(endpoint))[:16]}`（`TranslationCredentialStore.cs:257-263`）。
- 后端：`Win32CredentialBackend`（advapi32 `CredRead` / `CredWrite` / `CredDelete` / `CredEnumerate`）。
- 卸载清理：标准 Windows 卸载程序清理所有 `AIPDF-Translate-*` 前缀条目（需用户确认）。

### 持久化位置

`%APPDATA%\AIPDF\settings.json`，`translationProviders` 数组。**仓库内不提交 settings.json。** 相关默认字段：

```json
{
  "translationProviders": [
    { "provider": "deepseek", "endpoint": "https://api.deepseek.com/v1", "model": "deepseek-chat" }
  ],
  "translationDefaultSourceLanguage": "auto",
  "translationDefaultTargetLanguage": "zh",
  "translationTemplateId": "academic"
}
```

### URL 规范化要点

实现中必须处理的边界情况：

| 情况 | 用户输入 | 规范化结果 |
|---|---|---|
| 缺协议 | `api.openai.com/v1` | `https://api.openai.com/v1` |
| 尾部斜杠 | `https://api.deepseek.com/v1/` | `https://api.deepseek.com/v1` |
| 含完整路径 | `https://api.openai.com/v1/chat/completions` | `https://api.openai.com/v1` |
| `/v1` 重复 | `https://localhost:11434/v1/v1` | `https://localhost:11434/v1` |
| localhost vs 127.0.0.1 | `http://localhost:11434` / `http://127.0.0.1:11434` | 保持用户输入（但 loopback 校验两者均认可） |
| 空 key 占位符 | `(空)` / `sk-` | 视为无 key（本地可能不需要 key） |

### opencode 模式参考

opencode CLI 的供应商配置模式：

- **Catalog**：`models.dev` 的 `api.json`，预置 provider 列表（`{id, name, env[], api?, npm?, models{}}`）。
- **用户配置**：`provider` / `model` 字段选择。
- **凭据**：`auth.json` 按 provider id 为 key。

本项目的 v1.2 设计与此对齐：内置预设表（等同 catalog）+ 用户配置（`TranslationProviderConfig`）+ 凭据（Windows Credential Manager）。区别在于：opencode 的 catalog 来自外部 JSON 文件，本项目的预设表硬编码在代码中（无需网络拉取 catalog）。

## 协议与端点兼容

### 两种 API 协议

| 协议 | 请求路径 | 鉴权方式 | 响应格式 |
|------|----------|----------|----------|
| **OpenAI** | `POST {base}/chat/completions` | `Authorization: Bearer {key}` | OpenAI Chat Completions 格式 |
| **Anthropic** | `POST {base}/v1/messages` | `x-api-key: {key}`（或 `Authorization: Bearer {key}`） | Anthropic Messages 格式 |

Anthropic 协议还支持可选的 `anthropic-version` 请求头（如 `2023-06-01`），用于声明 API 版本。两种协议的请求体和响应体结构不同，**不能混用**。

### Provider 级协议与按模型覆盖

每个 provider 有一个默认 `apiProtocol`（`openai` 或 `anthropic`），在预设表中声明。当同一 provider 下不同模型使用不同协议时（如 opencode go：大部分模型走 OpenAI Chat Completions，MiniMax M3 / Qwen3.8 Max 等走 Anthropic Messages，Grok 4.5 / GPT-5.6 Luna 等走 OpenAI Responses），通过 `modelProtocols` 字典按模型名覆盖：

```
apiProtocol: "openai"                          ← provider 默认
modelProtocols: {
  "minimax-m3": "anthropic",
  "qwen3.8-max": "anthropic",
  "grok-4.6": "openai"
}
```

客户端在发起请求时，先查 `modelProtocols[model]`，未命中则用 provider 的 `apiProtocol`。

### 协议/端点不匹配的失败模式

若客户端用 OpenAI 协议请求 Anthropic 端点（或反之），典型表现为：

- **400 Bad Request**：请求体格式不兼容（如 OpenAI 的 `messages` 数组 vs Anthropic 的 `messages` + `max_tokens` 必填）。
- **404 Not Found**：路径不匹配（如请求 `/chat/completions` 但服务端只提供 `/v1/messages`）。

UI 应在收到 400/404 时自动检测当前 provider 的 `apiProtocol`，若与请求协议不一致则提示用户「当前端点使用的是 {协议} 协议，是否切换？」并提供一键修复。

### Base URL 形状规则

| 协议 | Base URL 形状 | 客户端拼接 |
|------|--------------|-----------|
| OpenAI | `{base}/chat/completions` | base 通常以 `/v1` 结尾 |
| Anthropic | `{base}/v1/messages` | **base 不以 `/v1` 结尾**（客户端自行拼接 `/v1/messages`） |

对于 OpenAI 协议，base URL 就是用户填写的端点地址（通常含 `/v1`）。对于 Anthropic 协议，大多数 provider 的 base URL **不含** `/v1` 后缀（如 `https://api.anthropic.com`），客户端在构建请求时拼接 `/v1/messages`。预设表中已为每个 provider 标注正确的 base URL 形状。

## 编程套餐合规约束

### 官方限制说明

GLM Coding Plan 和 Kimi Code 属于**订阅 / 编程套餐**，官方 FAQ 明确限制使用范围。合规警示原文：

> 此端点属于订阅 / 编程套餐，仅限官方支持的工具使用。自建应用通过 API 调用可能不计入套餐额度（GLM 会返回 1113 Insufficient Balance）。如需在本应用使用，请改用标准 API 端点。

### 后果

- **GLM**：自建应用通过 Coding Plan 端点调用，不消耗套餐额度，返回错误码 `1113 Insufficient Balance`（余额不足），实际是配额未被识别。
- **Kimi Code**：类似限制，要求应用具有真实工具身份（genuine tool identity），自建应用不满足条件。

### 产品决策

- **端点仍然包含**在预设表中（用户有知情选择权），但**默认不选中**套餐端点。

## 安全与合规边界

> 完整安全约定沿用 v1.1 `需求总结.md` §安全边界（不可信输入）与 §云端配置复用与同意，此处仅列 v1.2 相关约束。

### 不变的安全不变量

1. **API Key 仅存 Windows Credential Manager**；地址 = `AIPDF-Translate-{provider}-{sha256(origin)[:16]}`。
2. **Key 仅经 stdin 传递**给 Python 子进程；不进 argv / 环境变量 / 日志 / 配置文件 / 崩溃转储 / 会话恢复 / recent / presets。
3. **同意绑定**：`provider + endpoint-origin + key-fingerprint`（SHA-256 前 16 hex）；180 天 TTL；endpoint 主机名/协议/端口任一变更 → 重新同意；仅改模型名 → 不重置；改 key → 同意失效。
4. **云端要求 HTTPS**（loopback 可用 HTTP）。
5. **禁止在 endpoint URL 中内嵌密钥**（`?api_key=xxx` / `user:pass@host`）；保存时校验，命中则拒绝。
6. **本地端点必须 loopback**（`127.0.0.1` / `::1` / `localhost`）；非 loopback 不得以「本地」名义绕过云端同意。

### v1.2 新增安全约束

7. **模型列表拉取请求不携带 API Key**：`GET {base}/v1/models` 是公开端点（本地服务器）或无需认证的端点（部分云端）；若拉取失败（401/403），提示用户手动输入模型名，**不自动发送 key 到未确认的端点**。
8. **预设表 base URL 校验**：内置预设的 base URL 在首次使用时与用户实际填写的 URL 做 origin 比对；若用户修改了预设的 base URL（指向不同服务器），该配置视为「自定义」，不享受预设的信任便利（如自动填充环境变量名）。

### 「测试连接」与「拉取模型」的安全规则

- 两者均为**用户显式触发**的动作，不自动执行、不在后台轮询。
- **本地（loopback）**：请求**不携带密钥**（Ollama / LM Studio / vLLM / llama.cpp 默认无鉴权）。
- **云端**：请求**会携带已保存的密钥**（OpenAI 兼容端点鉴权必需），但**不发送任何文档内容**——只做最小连通性/凭据校验。
- 仅允许 `https`；非 loopback 的明文 http 一律拒绝（沿用既有约束）。
- 密钥仅来自系统凭据管理器、经内存直接使用；**不写入配置、日志、命令行或环境变量**。
- 该动作**不替代**文档上传同意：首次实际翻译仍走既有的云端同意流程（同意绑定 provider + endpoint + 密钥指纹）。
- 拉取失败（401/403/超时）时**不回退**为发送文档；仅提示错误并允许重试。
