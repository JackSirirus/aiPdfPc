## 1 概述

### 1.1 背景

AIPDF 目前是一个"工具优先"的工作台：打开应用先选工具，再拖文件、调参数、处理。文档只是工具的输入，阅读场景完全缺位——没有连续滚动阅读、目录、书签、全文搜索和批注。日常"打开一份 PDF 看看"的最小诉求都必须先经过工具选择流程，本末倒置【D1】。

用户意图：**把应用从 PDF 工作台变成 PDF 阅读器，但 32 个工具一个不丢**。本质是信息架构倒转：从"工具为中心"变为"文档为中心"，工具降级为文档上下文中的操作【D2】。

当前状态与目标状态对比：

| 维度 | 当前状态（v0.x） | 目标状态（v1.0） |
|------|------------------|------------------|
| 主界面 | 工具选择器 | 阅读视图 / 起始页 |
| 文档角色 | 工具的输入参数 | 一级实体，工具挂到文档上下文 |
| 阅读能力 | 无（仅工具预览区） | 连续滚动、缩略图、目录、书签、搜索、批注 |
| 工具入口 | 独立选择器页面 | 四通道（右抽屉/向导/选中浮菜单/临时标签）+ 起始页网格 |
| 多文档 | 不支持 | 多标签页 |
| 状态记忆 | 无 | 阅读状态 + 会话恢复 |
| 批注 | 不支持 | 高亮 + 笔记，就地写回原文件 |
| 打印 | 不支持 | 基于渲染栈分页位图 |
| 文件关联 | 无 | 注册"用 AIPDF 打开"，单实例互斥 |

v1.0 聚焦 Windows 平台（WPF），macOS 端同步重构延后【D10】。视觉风格沿用方案 A tokens【D9】。v1.0 阅读器为唯一主界面，32 个工具全部挂到文档上下文中。

### 1.2 目标

1. 打开 PDF 即进入沉浸阅读：连续滚动、缩略图/目录/书签、全文搜索。
2. 32 个工具无损保留，以文档上下文方式进入（四通道 + 起始页工具网格）。
3. 批注（高亮 + 笔记）就地写回原 PDF（引擎原子保存），防抖自动保存走独立快速通道。
4. 阅读状态跨会话记忆 + 会话恢复（标签集合、窗口状态、左栏宽度）。
5. 处理结果即文档：输出 PDF 自动开新标签进入阅读流。
6. 支持打印当前文档；注册"用 AIPDF 打开"文件关联（单实例）。

## 2 信息架构

### 2.1 文档中心模型

v1.0 的信息架构以**文档**为一级实体，**工具**降级为文档上下文中的操作【D2】。

顶层结构（文字描述）：

```
+-----------------------------------------------------------+
|  顶栏：品牌 | 标签栏（多标签） | + | search | gear       |
+----------+-----------------------------------------------+
|  左栏    |  主区                                         |
|  四面板  |  PDF 渲染画布（连续滚动）                      |
|  缩略图  |  -- 或 --                                     |
|  目录    |  右抽屉（单文件工具内联参数）                  |
|  书签    |  -- 或 --                                     |
|  搜索    |  模态向导（多文件/多步工具）                    |
|          |  -- 或 --                                     |
|          |  临时标签（复杂编辑工具）                       |
+----------+-----------------------------------------------+
|  状态栏：savepill（保存状态） / 页码 / 缩放              |
+-----------------------------------------------------------+

无文档时：
+-----------------------------------------------------------+
|  起始页（打开按钮 + 最近文件 + 常用工具网格 + 32 工具）   |
+-----------------------------------------------------------+
```

### 2.2 四通道定义与判据优先级

工具进入文档上下文的四条通道定义如下（完整 32 工具映射见 01 映射表）：

| 通道 | 定义 | 判据 | 典型工具 |
|------|------|------|----------|
| 起始页 | 无 PDF 输入的工具，仅在无文档时展示 | 判据 1：extensions 不含 pdf | 扫描为 PDF、图片转 PDF、Word/PPT/Excel 转 PDF、HTML 转 PDF |
| 右抽屉 | 单文件工具，内联参数面板【D7】 | 判据 4：单文件 | 排列页面、PDF 转 PDF/A |
| 模态向导（可简称向导） | 多文件或多步工具【D4】 | 判据 3：multiple=True 或 id="workflow" | 合并、拆分、删除、提取、压缩、修复、OCR、转换类、旋转、页码、水印、签名、遮盖、比较、工作流程 |
| 临时标签 | 复杂编辑工具，复用现有工具页，每标签页面实例缓存【D16】 | 判据 2：edit/forms/crop | 裁剪、编辑、表单 |

**判据优先级**（先匹配先得，从 01 映射表转录）：

1. 无 PDF 输入（extensions 不含 pdf）→ 起始页
2. 复杂选择/交互（edit/forms/crop）→ 临时标签
3. 多文件或多步（multiple=True 或 id="workflow"）→ 向导
4. 单文件 → 右抽屉

> 通道分布：起始页 6 / 右抽屉 2 / 向导 21 / 临时标签 3 = 32 工具。完整映射表见 01。

### 2.3 标签宿主概述

`MainWindow` 的 `ToolPageHost`（ContentControl）位改造为标签页宿主（TabControl 方向）【D16】。每标签页面实例缓存，registry 现状每次重建会丢临时标签的工具状态，改为持久缓存后可避免此问题。详见第 4 章技术架构。

标签栏行为：关闭标签时若未保存批注则提示保存【D8】；最后一个文档标签关闭后回落到起始页【D3】；临时标签关闭后不回落到起始页。

### 2.4 多标签去重

重复打开同一文件时，激活现有标签而非创建新标签，按路径去重【D14】。路径相同但文件内容已变更（size/mtime 变化）时，仍复用已有标签并触发重载。

### 2.5 最近列表

起始页展示最近打开的文件列表，上限 20 条【D15】。列表按最近打开时间倒序排列，每条显示文件名、路径摘要、最后打开时间、阅读进度元信息。清空需二次确认弹窗。

### 2.6 单实例与文件关联概览

注册"用 AIPDF 打开"（.pdf 文件关联）【D21】。单实例互斥是文件关联的连带必须项。安装逻辑改动须跑 `tests/test_installer.py`。完整规格详见 3.9 节。

### 2.7 起始页空态概览

无文档打开时，起始页作为唯一主界面展示【D3】。包含四个区域：打开按钮、最近文件卡片（上限 20 条【D15】）、常用工具网格（v1.0 静态清单【R19】）、全部 32 工具入口。

## 3 功能需求
### 3.1 基础阅读包【D11】

#### FR-01 连续滚动阅读

**描述**

PDF 文档以连续滚动方式呈现。页面自上而下排列，页间距 16px，无翻页动画。视口中占比最大的页面为「当前页」，状态栏页码与缩略图选中态同步跟随滚动位置。

**交互与状态**

- 滚轮/触摸板触发连续滚动；PageUp/PageDown、方向键整页翻动（视口对齐）。
- 当前页判定：视口中面积占比最大的页；缩略图面板同步高亮对应缩略图。
- 虚拟化：仅可视页 ± 缓冲页持有位图，未渲染页显示骨架占位（保持正确宽高比，避免跳动）。
- 渲染队列优先级：可视区 > 翻页方向邻近页 > 缩略图。
- 相关状态：【ST-09】连续滚动阅读基准态；【ST-10】快速滚动到未渲染页占位态。

**边界与失败路径**

- 快速滚动至未渲染页：骨架屏占位，渲染完成直接替换无闪烁【ST-10】。
- 大文档（500+ 页）：缩略图仅渲染可视区 ±3 页；目录/书签/搜索列表内滚动。
- 窗口极小尺寸：左栏折叠为窄条图标，右抽屉自动收起为悬浮按钮；阅读区最小 480px。
- 渲染管线技术约束详见第 4 章。

**验收标准**

- AC-01.1：打开 12 页 PDF，滚动至第 6 页占比最大 → 状态栏显示「6/12」，缩略图第 6 项蓝色外描边。
- AC-01.2：打开 500 页 PDF，快速滚动到第 300 页 → 占位符保持正确宽高比，渲染完成后无闪烁替换。
- AC-01.3：窗口宽度缩至 500px → 左栏折叠为图标条，右抽屉收起，阅读区宽度不小于 480px。

#### FR-02 缩略图面板

**描述**

左栏第一面板为缩略图，以卡片形式展示每页预览。当前页缩略图带蓝色外描边。底部状态行显示页数、体积、文本层判定结果。

**交互与状态**

- 缩略图按文档页序纵向排列，卡片底部显示页码。
- 点击缩略图 → 阅读区滚动至对应页顶部。
- 高亮批注在缩略图中以黄色背景标识。
- 底部状态行：「12 页 · 1.8 MB · 可搜索」或「无法搜索」（无文本层时）。

**边界与失败路径**

- 无文本层文档：状态行显示「无法搜索」。
- 渲染中：骨架屏占位，完成后替换。

**验收标准**

- AC-02.1：点击第 3 页缩略图 → 阅读区滚动到第 3 页顶部，缩略图第 3 项蓝色外描边。
- AC-02.2：第 2 页有高亮批注 → 缩略图第 2 项显示黄色背景标识。

---

#### FR-03 目录面板

**描述**

左栏第二面板为目录，读取 PDF 内建大纲（Outline）。仅读取文档自带大纲，不提供自动生成或目录编辑功能。

**交互与状态**

- 目录条目按层级缩进（lv1 加粗，lv2 次级缩进 + 灰色）。
- 点击条目 → 阅读区滚动至对应页。

**验收标准**

- AC-03.2：打开无大纲 PDF → 目录面板显示「此文档没有目录」空态文案。

#### FR-06 缩放控制【R18】

**描述**

缩放阶梯为 25/33/50/67/100/150/200/300/400%（九档）。另有「适配宽度」与「适配页面」两个动态档。

**交互与状态**

- Ctrl+滚轮逐档切换（向上放大，向下缩小）。
- 状态栏 +/− 按钮逐档切换。
- 「适配宽度」：按窗口宽度重算 zoom 值。
- 「适配页面」：按窗口高度重算 zoom 值。
- 手动缩放后脱离适配档（按钮不再高亮）。
- 到达阶梯端点（25% 或 400%）：按钮置灰禁用，Ctrl+滚轮不再变化【ST-11】。
- 缩放值随阅读状态记忆持久化。

**边界与失败路径**

- 窗口 resize 时适配档自动重算。
- 400% × 150%DPI = 5052px 超 4096px 纹理上限 → 渲染层分块或限幅（技术详见第 4 章）【R9】。

**验收标准**

- AC-06.1：在 100% 状态按 Ctrl+滚轮向上一次 → 跳至 150%；继续向上 → 200% → 300% → 400% → 按钮置灰。
- AC-06.2：在 25% 状态按 Ctrl+滚轮向下 → − 按钮置灰，zoom 停留在 25%。
- AC-06.3：点击「适配宽度」→ zoom 值匹配窗口宽度；手动缩放到 150% → 「适配宽度」按钮不再高亮。

### 3.3 全文搜索【D6】【D12】

#### FR-09 搜索激活与面板接管

**描述**

Ctrl+F 或点击顶栏搜索框激活搜索。左栏第四面板「搜索」自动接管（缩略图/目录/书签顺延隐藏），显示命中列表 + 页内高亮【ST-13】。

**交互与状态**

- 搜索激活时左栏切换为「搜索」面板，面板顶部显示搜索框 + 导航（前进/后退 + 「N / M」计数）。
- 输入关键词后防抖 300ms 触发检索。
- 命中项 = 页码 + 上下文摘录（关键词加粗高亮）。
- 当前命中项在列表中以浅蓝背景标识，页内同步橙框高亮。
- 回车跳下一处 / Shift+回车上一处。
- Esc / 面板 × 退出搜索：清除页内高亮，左栏恢复原面板（缩略图/目录/书签，取决于搜索前选中哪个）。

**边界与失败路径**

- 无结果：列表显示空态「未找到「关键词」」，引导「试试其他关键词，或检查全文是否为图片型页面」【ST-14】。
- 命中 >200 条：列表截断，头部提示「共 N 处，显示前 200 处，请细化关键词」。
- 大文档首次检索：索引构建过渡态，面板显示 spinner「正在检索 N 页…」【ST-16】。索引构建一次、会话内复用。

**验收标准**

- AC-09.1：在 12 页文档中搜索「转化率」→ 左栏切换为搜索面板，列表显示命中项，页内橙框高亮当前命中。
- AC-09.2：按 Esc → 搜索面板消失，左栏恢复为之前的面板（如缩略图），页内橙框清除。
- AC-09.3：搜索不存在的关键词 → 空态提示「未找到「xxx」」。

#### FR-10 搜索降级与无文本层处理【D12】【R13】

**描述**

无文本层文档（扫描件未 OCR）搜索整体禁用。三要素降级策略：(1) 搜索框置灰禁用；(2) 引导「去 OCR」文案；(3) 乱码率启发式判定。此为对抗性审查抓出的信任崩塌风险，必须写透。

**交互与状态**

- 检测到无文本层时：搜索框置灰，占位文案改为「此文档无文本层，搜索不可用」【ST-15】。
- Ctrl+F 聚焦时显示引导 Toast（警告 6s）：「扫描件无法搜索 · 可先运行 OCR 识别生成文本层」，附「去 OCR →」动作按钮。
- 「去 OCR」→ 右抽屉定位到 OCR 工具并展开参数面板（输入已预填当前文档）。
- OCR 完成 → 结果开新标签（有文本层），Toast「已可搜索」。

**乱码率启发式**

- 文本提取后计算乱码率：不可见控制字符 + 替换字符占比 > 阈值 → 判定为低质量文本层。
- 阈值由实施期 spike 校准（建议初始值 15%）。
- 乱码率高时同样走降级路径：搜索框置灰 + 引导 OCR，不执行检索。

**降级策略的信任崩塌风险**

CJK 文档的静默失效是最危险的搜索场景：用户输入中文关键词，文档有文本层但提取质量极差（乱码率高），搜索返回空结果。用户会认为「文档里没有这个内容」，而非「搜索功能坏了」。这是信任崩塌，比功能缺失更严重。

防护层：
1. 乱码率启发式检测 → 高乱码率时禁用搜索 + 引导 OCR（与无文本层同路径）。
2. 搜索框占位文案明确告知「搜索不可用」，不假装正常。
3. Toast 引导给出下一步出口（去 OCR），不给用户留下「没搜到」的错觉。
4. OCR 结果开新标签后新标签可搜索，形成闭环【R13】。

**边界与失败路径**

- 混合文档（部分页有文本层）：按页判定，有文本层的页正常搜索，无文本层的页跳过（不在列表中显示该页命中）。
- OCR 完成但乱码率仍高：新标签仍走降级路径，Toast 提示「OCR 完成但文本质量较低，搜索可能不完整」。

**验收标准**

- AC-10.1：打开纯扫描件 PDF → 搜索框置灰「此文档无文本层，搜索不可用」，Ctrl+F 引导 Toast + 「去 OCR →」。
- AC-10.2：点击「去 OCR」→ 右抽屉展开 OCR 工具面板，输入预填当前文档；OCR 完成后新标签可搜索。
- AC-10.3：打开有文本层但乱码率 >15% 的 PDF → 搜索框置灰 + 引导 OCR，不执行检索。
- AC-10.4：混合文档（第 1-5 页有文本层，第 6-10 页无）→ 搜索仅返回第 1-5 页命中。

#### FR-12 工具子菜单与页码预填

**描述**

选中浮菜单「用工具处理」子菜单展开后，显示常用工具快捷入口 + 「更多工具…」链接。选中工具后进入对应通道（右抽屉/向导），页码范围预填当前页。

**交互与状态**

### 3.5.1 就地写回原文件 【D17】

**FR-13** 批注以 PDF 标准注释（Highlight + FreeText）形式写回当前打开的源文件，不另存副本。

- 副本方案语义崩塌（批注归属不明、多版本混乱），裁决后选择就地写回。这是对「源文档只读」项目约定的一次显式豁免：批注写回场景下，维护者豁免只读约定，仅限本节描述的批注保存链路。其余工具链（合并、拆分、压缩、OCR 等）仍遵守源文档只读，输出走独立任务目录。

> ⚠ **维护者豁免重申**：`AGENTS.md` 要求「源文档只读；每次输出进入新的任务目录，不覆盖原件」。批注保存是唯一例外，范围限定为：(a) 用户在阅读器中主动创建的高亮或笔记；(b) 引擎原子保存（临时文件→`os.replace`→`fsync`）；(c) 保存前冲突检测。除此三条约束外的写回操作一律禁止。PRD 此处记录豁免及其边界，后续维护者修改时须核对本段。

引擎注释操作新增：`add_highlight_annot`（高亮，含颜色参数）和 `insert_text`（FreeText 笔记，含矩形位置与内容）。技术详见第 4 章 T4 契约。

批注类型细节：
- **高亮**：用户拖选文字后点击「高亮」，引擎在 PDF 对应位置添加 Highlight 注释，颜色默认为黄色（#FFFF00），支持后续编辑颜色
- **文字笔记**：用户拖选文字后点击「笔记」，引擎同时添加 Highlight 注释（关联选区）和 FreeText 注释（笔记内容），笔记以弹层形式展示在高亮旁边
- **删除**：用户悬停批注标记/高亮时显示编辑/删除按钮，点击删除即时从叠加层移除，待下次保存时从 PDF 文件中删除对应注释

**AC-13.1** 用户添加高亮或笔记后，引擎将注释写入源 PDF 文件；写入完成后文件仍为合法 PDF，可用其他 PDF 阅读器打开并看到注释。

**AC-13.2** 加密文档（打开时已提供密码）保存批注后仍保持加密状态，密码与原文件一致。引擎 `save_pdf` 现强制 `PDF_ENCRYPT_NONE`，须新增加密保存参数（技术详见第 4 章 T4 契约）。

**AC-13.3** 写入失败时客户端叠加层批注保留，不丢失；用户可重试或另存为副本。

### 3.5.2 2 秒防抖自动保存 【D8】

**FR-14** 用户最后一次批注操作（新增、编辑、删除任一）后计时 2 秒；期间无新操作则触发保存提交。每次新操作重置计时器。

> R16 已入正文：防抖起点为「最后一次批注操作」而非「首次批注」。这意味着用户连续编辑多条批注时，计时器从最后一次操作开始算，而非第一次。好处是用户在编辑过程中不会被中途打断提交。

防抖的具体行为：
- 用户添加第 1 条高亮 → 计时器启动（2s）
- 1s 后用户添加第 2 条高亮 → 计时器重置（从 0 重新计 2s）
- 1.5s 后用户添加第 3 条笔记 → 计时器再次重置
- 2s 无操作 → 提交保存（3 条批注合并为一次引擎请求）
- 期间翻页、缩放、搜索等非批注操作不影响计时器

**AC-14.1** 连续添加 3 条高亮（间隔均 < 2s），savepill 在最后一次操作后 2s 切换为「保存中…」，仅提交一次（三条批注合并）。

**AC-14.2** 2s 内用户翻页、缩放、搜索等非批注操作不重置防抖计时器。

**AC-14.3** 用户添加批注后立即关闭标签，防抖计时器被跳过，直接提交保存（关闭时强制保存）。

### 3.5.3 独立快速通道（不在全局队列） 【D25】【R2】

**FR-15** 批注保存走独立快速通道，不进入全局串行任务队列。引擎层面一进程一请求，允许并发子进程（文件级互斥）。

> R2 教训：若批注保存进全局串行队列，排队期间 `IsRunning` 检查会静默丢弃新保存请求，导致批注丢失。这是致命风险组合——`IsRunning` 静默丢弃 + 串行队列无超时，两个问题叠加在一起就是数据丢失。裁决后批注保存与工具任务完全解耦，批注保存有自己的超时计时（30s）和独立的引擎请求通道。

快速通道的实现要点：
- 批注保存请求不经过全局队列管理器，直接提交给 EngineBridge
- EngineBridge 维护独立的请求槽位，与全局队列的请求槽位互不干扰
- 文件级互斥：同一文件的批注保存请求串行执行（防止并发写入冲突），不同文件的批注保存请求可并行
- 批注保存的 30s 超时由 WPF 侧计时，引擎无内部超时（引擎桥接契约）

**AC-15.1** 用户在工具执行排队期间添加批注，保存请求不被排队阻塞，独立提交引擎。

**AC-15.2** 批注保存与全局队列中的工具任务可并行执行，互不干扰。

### 3.5.4 30 秒超时转失败

**FR-16** 批注保存请求提交后启动 30 秒 WPF 侧计时（引擎无内部超时，技术详见第 4 章 T4）。超时未收到成功响应则转失败重试态。

完整失败用户旅程：
1. 防抖 2s 后提交引擎，savepill 切换为「保存中…」
2. WPF 侧启动 30s 计时器
3. 若 30s 内引擎无响应（进程崩溃、文件被锁、磁盘错误）：
   - 客户端取消引擎子进程（`taskkill` 子进程树）
   - savepill 切换为「保存失败 · 点击重试」
   - Toast 弹出错误提示 8s，含「重试」和「另存为…」动作按钮
   - 客户端叠加层批注保留，用户可继续阅读
4. 用户点击 savepill 或 Toast「重试」，重新提交保存请求（回到步骤 1）
5. 连续失败 3 次 → Toast 升级为「建议另存为副本」，附「另存为…」动作按钮
6. 用户点击「另存为…」→ 弹出文件保存对话框 → 保存到新路径 → 叠加层清除 → 原文件保持不变

超时计时的精确语义：
- 计时起点：EngineBridge 发送请求的时刻
- 计时终点：收到引擎 stdout 成功响应的时刻
- 超时判定：30s 内未收到成功响应（无论引擎是否仍在运行）
- 超时后动作：`taskkill` 子进程树 + 切换 savepill 为失败态

**AC-16.1** 引擎进程崩溃或文件被锁导致 30s 无响应，savepill 切换为「保存失败 · 点击重试」。

**AC-16.2** 超时后客户端取消引擎子进程（`taskkill` 子进程树），并保留叠加层批注不丢失。

### 3.5.5 引擎原子保存 【D17】

**FR-17** 引擎写入批注时执行原子保存：先写临时文件，成功后 `os.replace` 覆盖原文件，再 `fsync` 确保落盘。任一步骤失败不影响原文件完整性。

> 技术实现细节（临时文件命名规则、替换顺序、错误恢复）归 T4 契约，本节只写行为面。

原子保存的完整流程：
1. 引擎接收保存请求（含文件路径、批注数据、密码）
2. 生成临时文件路径（同目录下 `.aipdf_tmp_{随机名}`）
3. 读取原文件 → 添加/修改注释 → 写入临时文件
4. 临时文件 `fsync` 确保数据落盘
5. `os.replace(临时文件, 原文件)` 原子替换
6. 原文件 `fsync` 确保替换操作落盘
7. 删除临时文件（如果还存在）
8. 返回成功响应

错误恢复：
- 步骤 3 失败：临时文件可能残留，原文件不受影响
- 步骤 5 失败：`os.replace` 是原子操作，要么成功（原文件被替换），要么失败（原文件不变）
- 步骤 6 失败：替换已完成但未 fsync，数据可能在断电后丢失（概率极低）
- 步骤 7 失败：临时文件残留，下次启动时清理

**AC-17.1** 保存过程中断电或进程终止，原文件不被损坏（临时文件被清理或残留，原文件保持断电前状态）。

**AC-17.2** 保存成功后临时文件被清理，磁盘上仅保留更新后的原文件。

### 3.5.6 保存前 size/mtime 冲突检测 + 冲突对话框 【D17】【R10】

**FR-18** 保存前校验文件 size 与 mtime 是否与打开时一致。若不一致（外部程序修改过文件），弹出冲突对话框。

> R10：外部修改并发冲突 + 双实例。单实例互斥为连带必须项（决策 21），防止两个 AIPDF 实例同时修改同一文件。

冲突检测的时机：每次批注保存提交前（防抖 2s 后），EngineBridge 在发送保存请求前先读取文件当前 size 和 mtime，与打开时记录的值对比。任一不一致则触发冲突对话框。

冲突检测的精度：
- size 检测：文件字节数变化（外部程序修改内容、保存、格式转换等）
- mtime 检测：文件修改时间变化（任何写操作都会更新 mtime）
- 两者任一不一致即判定冲突（宁可误报不可漏报）
- 检测在引擎请求发送前执行（不消耗引擎资源）

冲突对话框内容：
- 主文案：「文件自打开后已被外部程序修改」
- 副文案：显示「上次保存时间：YYYY-MM-DD HH:MM」
- 按钮：「覆盖保存」/「另存为…」/「取消」
- 对话框为模态，阻塞批注保存流程直至用户选择

覆盖保存 = 用户明确知晓外部修改被覆盖，继续原子写入。另存为 = 保存到新路径，原文件不变。取消 = 批注保留叠加层，等待下次保存机会。

**AC-18.1** 用户在 AIPDF 打开文件的同时用其他程序修改并保存同一文件，AIPDF 批注保存时弹出冲突对话框。

**AC-18.2** 用户选择「覆盖保存」则继续执行原子写入；选择「另存为…」则弹出文件保存对话框；选择「取消」则批注保留叠加层，不写入。

### 3.5.7 savepill 三态 【D8】

**FR-19** 状态栏 savepill 随批注保存状态切换三种形态：保存中（绿色闪烁点 +「保存中…」）→ 已保存（绿色点 +「批注已保存」/「批注已保存 · 刚刚」）→ 失败重试（红色背景 +「保存失败 · 点击重试」）。

savepill 三态转录自全状态 HTML 设计参考：
- **ST-20（已保存）**：`.savepill.ok`，绿色点，文案「批注已保存 · 刚刚」
- **ST-21（保存中）**：`.savepill.bus`，绿色点闪烁（`animation: blink 1s infinite`），文案「保存中…」
- **ST-22（失败）**：`.savepill.fail`，红色背景 `#FCE8E6` + 红字 `#A50E0E`，文案「保存失败 · 点击重试」，`cursor: pointer`

此外，文件只读/被占用时 savepill 显示第四态：
- **ST-08（只读）**：`.savepill.fail`，文案「🔒 只读 · 批注不可用」；选中浮菜单隐藏「高亮/笔记」。

savepill 状态转换规则：
- 默认状态（无批注或已保存）：savepill 隐藏，不显示
- 用户添加/编辑/删除批注后：savepill 显示「● 批注已保存 · 刚刚」（ST-20）
- 2s 防抖后提交保存：savepill 切换为「● 保存中…」（ST-21，绿色闪烁）
- 保存成功：savepill 切换为「● 批注已保存」（ST-20，绿色常亮），2s 后隐藏

- 文件只读：savepill 常驻「🔒 只读 · 批注不可用」（ST-08，红色常亮）

savepill 的交互：
- ST-20（已保存）：不可点击，仅展示状态
- ST-21（保存中）：不可点击，防止重复提交
- ST-22（失败）：可点击，点击后重新提交保存请求（回到 ST-21）
- ST-08（只读）：不可点击，仅展示状态

**AC-19.1** 保存成功后 savepill 显示「批注已保存」2s，然后自动消失（恢复为默认状态栏）。

**AC-19.2** 连续失败 3 次后 Toast 升级为「建议另存为副本」，附「另存为…」动作按钮。

### 3.5.8 以 PDF 注释为唯一真相源 【D19】【R14】

**FR-20** 批注保存成功后，客户端叠加层清除对应批注，以 PDF 文件内嵌注释作为唯一渲染源。防止 `WithAnnotations=true` 导致双重渲染（同一条高亮显示两次）。

> R14：保存后双重渲染 + 滚动丢失。裁决后并入批注保存链路约束：叠加层清除 + 重载保留视口。

唯一真相源的完整流程：
1. 用户添加批注 → 客户端叠加层渲染（即时可见，不等引擎）
2. 2s 防抖后提交引擎保存
3. 引擎保存成功 → 叠加层清除对应批注（从 Canvas 移除）
4. 从 PDF 文件重新加载注释（通过渲染栈的 `WithAnnotations=true`）
5. 此时页面上显示的批注完全来自 PDF 文件内嵌注释，无重复

为什么需要这个流程：
- 客户端叠加层和 PDF 内嵌注释是两套独立的渲染源
- 如果保存成功后不清除叠加层，同一条高亮会显示两次（叠加层一次 + PDF 注释一次）
- 清除叠加层后，PDF 注释成为唯一渲染源，保证数据一致性

**AC-20.1** 保存成功后用户在页面上看到的批注数量与保存前一致（注释从 PDF 文件渲染），无重复、无遗漏。

**AC-20.2** 保存成功后视口位置（当前页、滚动偏移）保持不变，不跳页。

### 3.5.9 工具执行前强制 flush 批注 【R11】

**FR-21** 任何工具（压缩、拆分、旋转、转 Word、redact 等）执行前，系统强制提交当前所有未保存的批注。flush 成功后才允许工具启动。

> R11 教训：redact 会删除全部既有批注（引擎现状事实）。若批注未保存就被 redact 处理，用户批注静默丢失且无法恢复。flush 是唯一防线。这个风险的严重性在于：批注是用户的认知劳动，丢失不可逆。

flush 的具体行为：
- 用户点击工具「开始」时，检查是否有未保存的批注
- 若有：提交保存请求 → 等待成功（最多 30s）→ 成功后启动工具
- 若无：直接启动工具
- flush 失败时：阻止工具启动，Toast 提示「批注保存失败，请重试」
- 用户可选择「强制继续（批注可能丢失）」或「取消」
- 强制继续 = 跳过 flush，直接启动工具（批注可能在工具执行过程中丢失）

flush 与防抖的关系：
- 若用户刚添加批注且防抖计时器仍在运行，flush 会跳过防抖，立即提交保存
- flush 不重置防抖计时器（flush 是独立的强制保存，不是用户操作）
- flush 成功后，防抖计时器被取消（因为已经保存了）

涉及 flush 的工具列表（非穷举）：
- 压缩（compress）
- 拆分（split）
- 合并（merge）
- 旋转（rotate）
- 转 Word/PPT/Excel
- OCR
- 永久遮盖（redact）← 最关键，会删除全部批注
- 裁剪（crop）← 可能裁出批注所在的区域
- 其他编辑类工具

**AC-21.1** 用户添加批注后立即点击工具「开始」，系统先提交批注保存请求并等待成功，再启动工具执行。

**AC-21.2** flush 超时（30s）或失败，阻止工具启动并弹出 Toast 提示「批注保存失败，请重试」；用户可选择「强制继续（批注可能丢失）」或「取消」。

### 3.5.10 redact 删除全部既有批注 → UI 明示警告 【R11】

> ⚠ 此条属 R11 落实要求，横跨批注节与工具执行节。本节记录 UI 行为面，引擎面事实见 4.4.4 关键事实表。

**FR-22** 用户触发 redact 工具时，若当前文档存在批注（无论是否已保存），UI 弹出警告对话框：「永久遮盖（redact）将删除文档中的全部批注。此操作不可撤销。是否继续？」

对话框按钮：「继续 redact」/「取消」。

为什么 redact 会删除批注：
- redact 引擎操作会重新生成 PDF 页面（遮盖区域被永久覆盖）
- 重新生成过程中，原有注释（Highlight/FreeText）不会被保留（引擎现状）
- 这是不可逆的操作，用户必须明确知晓后果

警告对话框的设计要点：
- 对话框为模态，阻塞 redact 流程直至用户选择
- 主文案明确告知后果：「将删除文档中的全部批注」
- 副文案补充：「此操作不可撤销」
- 按钮 1：「继续 redact」（确认删除批注）
- 按钮 2：「取消」（不执行 redact，返回参数面板）
- 对话框不提供「先保存批注再 redact」选项（flush 已在工具执行前强制完成）

**AC-22.1** 文档有批注时触发 redact，警告对话框必须出现；用户点「取消」则不执行 redact。

**AC-22.2** 文档无批注时触发 redact，不弹警告对话框，直接进入工具参数面板。

### 3.6.1 状态内容与持久化位置 【D20】

**FR-24** 应用为每个已打开的 PDF 文件记忆阅读状态，包括：最后阅读页码、缩放比例、左栏面板选择（缩略图/目录/书签/搜索）、书签列表（用户自建）。

- 标签关闭时保存当前阅读状态
- 应用退出时保存所有标签的阅读状态
- 阅读状态变更（翻页、缩放、切换面板、添加书签）时不实时写入磁盘，仅在上述两个时机批量写入

**AC-24.2** 阅读状态文件损坏或不可读时，静默忽略并重建空状态，不提示用户、不崩溃。

### 3.6.2 键设计：路径 + size/mtime 校验 【D20】【R6】

**FR-25** 阅读状态键 = 文件路径 + 文件 size + 文件 mtime。打开文件时用这三个字段校验状态有效性。

> R6 教训：仅用路径做键，同名文件内容不同会导致状态错配（自毁）。例如用户下载新版合同覆盖旧版，若仅按路径匹配，会恢复到旧版的阅读位置，而旧版第 47 页的内容可能完全不同于新版第 47 页。加入 size/mtime 双校验后，文件被替换或覆盖时旧状态自动失效。

键设计的完整公式：
```
状态键 = SHA256(文件路径 + "|" + 文件大小(字节) + "|" + 文件修改时间(Unix时间戳))
```

校验流程：
1. 打开文件时，读取当前 size 和 mtime
2. 用当前值计算状态键
3. 查找 `reading-state/{状态键}.json` 是否存在
4. 存在 → 恢复阅读状态
5. 不存在 → 从第 1 页开始，不恢复任何状态

**AC-25.1** 用户打开文件 A（100KB），关闭后将同名文件替换为另一份（200KB），再次打开时旧阅读状态不恢复（size 不匹配），从第 1 页开始。

**AC-25.2** 同一文件未修改（size/mtime 一致），重新打开时恢复上次阅读状态。

### 3.6.3 hash 惰性后台计算

**FR-26** 文件内容 hash 仅用于冲突检测场景（3.5.6 保存前校验），采用惰性后台线程计算，不阻塞打开流程。

> hash 不用于阅读状态键（键 = 路径 + size/mtime），仅在批注保存前作为冲突检测的辅助手段。惰性意味着用户打开文件时不会等待 hash 计算完成，阅读器立即响应；hash 在后台完成后缓存，供后续保存冲突检测使用。

hash 计算的详细流程：
1. 用户打开文件 → 立即显示第一页（不等 hash）
2. 后台线程启动 hash 计算（SHA256，读取整个文件）
3. hash 计算完成 → 缓存到内存
4. 用户添加批注 → 2s 防抖后触发保存
5. 保存前：读取当前文件 size/mtime → 与打开时对比
6. 若 size/mtime 不一致 → 弹出冲突对话框
7. 若 size/mtime 一致但用户选择「覆盖保存」→ 用缓存的 hash 做内容级比对

hash 计算的性能考虑：
- 大文件（>50MB）的 hash 计算可能需要数秒
- 后台线程不阻塞 UI 线程，用户可以正常阅读
- hash 计算完成后缓存，不重复计算
- 若文件在 hash 计算完成前被修改，hash 值可能过期，但不影响保存（保存前会重新校验 size/mtime）

**AC-26.1** 打开大文件（>50MB）时阅读器即时响应，不因 hash 计算而延迟显示第一页。

**AC-26.2** hash 计算完成后，若用户触发批注保存且检测到冲突，使用 hash 值做内容级比对。

### 3.6.4 孤儿 GC：90 天 / 上限 100 条 【D20】

**FR-27** 阅读状态目录定期执行孤儿 GC：删除超过 90 天未访问的状态文件，且状态文件总数上限 100 条。超出上限时淘汰最旧的条目。

> GC 触发时机：应用启动时检查一次。90 天未访问的状态大概率对应已不在用户工作流中的文件，保留无意义。上限 100 条防止状态目录无限膨胀。

GC 的具体行为：
- 启动时扫描 `%APPDATA%\AIPDF\reading-state\` 目录
- 读取每个 JSON 文件的最后访问时间（atime 或 mtime，取决于文件系统）
- 删除 90 天未访问的文件
- 若剩余文件仍超过 100 条，按访问时间排序，删除最旧的条目直到 100 条
- GC 过程静默执行，不提示用户

GC 的性能考虑：
- 100 个 JSON 文件的扫描和删除操作耗时 < 100ms（本地磁盘）
- GC 仅在启动时执行一次，不影响运行时性能
- GC 不删除当前打开文件的状态（即使超过 90 天）

GC 与阅读状态的关系：
- GC 删除的是「孤儿」状态（对应文件已不在用户工作流中）
- 当前打开文件的状态不会被删除（即使文件未在 90 天内访问）
- GC 后若用户再次打开已删除状态的文件，会从第 1 页开始（无状态恢复）

**AC-27.1** 状态目录有 105 条记录，GC 后保留最近访问的 100 条，最旧的 5 条被删除。

**AC-27.2** 状态目录有 80 条记录且全部在 90 天内访问过，GC 不删除任何条目。

### 3.7.1 会话内容与持久化位置 【D22】

  ],
  "window": {
    "width": 1200,
    "height": 800,
    "x": 100,
    "y": 50,
    "maximized": true
  },
  "leftPanel": {
    "width": 240,
    "activeTab": "bookmarks"
  }
}
```

### 3.13.1 全局串行队列 【D13】

**FR-40** 用户提交的工具任务（压缩、合并、转换、OCR 等）进入全局串行队列，同一时刻仅执行一个任务。后续任务排队等待，状态栏显示「排队中 · 第 N 位」。

> 串行原因：引擎桥接契约为一进程一请求，避免多任务并发导致资源争抢和状态混乱。引擎取消 = `taskkill` 子进程树，串行保证取消语义清晰。

队列行为细节：
- 新任务入队时，若队列为空且无任务执行中，立即启动
- 任务完成（成功/失败/取消）后，自动启动队列中下一个任务
- 状态栏显示当前执行任务的名称和进度，以及队列中等待的任务数
- 队列中任务的参数面板保持不变，用户可在排队期间调整参数
- 任务失败不自动重试，参数保留供用户修改后手动重试

**AC-40.1** 用户连续提交任务 A（压缩）和任务 B（合并），B 在 A 完成后自动开始，状态栏显示 B 的排队位置。

**AC-40.2** 队列中任务的参数面板保持不变，用户可在排队期间调整参数。

**AC-40.3** 队列有 3 个任务，第 1 个失败，第 2 个自动开始执行（不等待用户重试第 1 个）。

---

### 3.13.2 排队可见可取消 【D13】

**FR-41** 队列中每个任务在状态栏可见（任务名 + 排队位置），用户可取消队列中的任意任务（非当前执行任务）。

取消排队中的任务：从队列中移除，不执行，不产生任何副作用。
取消正在执行的任务：`taskkill` 子进程树，Toast 提示「任务已取消」；半成品保留在任务目录（不清理），用户可手动检查。

状态栏队列显示规则：
- 执行中：显示「正在执行：压缩 report.pdf」
- 排队中：显示「排队中 · 第 2 位：合并 3 份文件」
- 仅显示队列中前 3 个任务，超出部分用「…还有 N 个任务」省略
- 取消按钮：每个排队任务右侧显示「✕」按钮，点击取消

**AC-41.1** 队列有 3 个任务，用户取消第 2 个，第 3 个位置自动前移。

**AC-41.2** 取消当前执行中的任务时，`taskkill` 子进程树，Toast 提示「任务已取消」；半成品保留在任务目录。

### 3.13.3 取消仅当前任务、队列保留 【D13】

**FR-42** 取消操作仅移除被取消的任务，队列中其余任务保留并按序执行。不因单个取消清空整个队列。

为什么不能清空整个队列：
- 用户可能批量提交了 5 个压缩任务，只想取消其中一个
- 清空整个队列会丢失其他 4 个任务的参数配置
- 串行队列的设计就是「一个接一个执行」，取消单个不影响其他

**AC-42.1** 队列有 5 个任务，取消第 3 个，第 1/2 个继续执行，第 4/5 个保持排队。

**AC-42.2** 取消当前执行任务后，队列中下一个任务自动开始。

### 3.13.4 批注保存不在队列（快速通道） 【D25】【R2】

**FR-43** 批注保存不进入全局串行队列，走独立快速通道（3.5.3 FR-15）。批注保存与工具任务可并行执行。

> R2 规避说明：若批注保存进队列，当队列中有耗时任务（如 OCR 大文件）时，批注保存被阻塞 30s+ 必然超时转失败，用户批注丢失。独立快速通道 + 30s 超时是 R2 的直接解决方案。这里的关键洞察是：批注保存是高频低延迟操作（通常 < 1s），工具任务是低频高延迟操作（可能 30s+），两者混在同一个队列里对批注用户不公平。

队列与快速通道的边界：
- 工具任务（压缩/合并/转换/OCR 等）→ 全局串行队列
- 批注保存 → 独立快速通道（不排队、不阻塞、独立超时）
- 两者互不干扰，可并行执行
- 批注保存的引擎请求与工具任务的引擎请求可同时存在于 EngineBridge

**AC-43.1** 队列中有工具任务执行中，用户添加批注，保存请求不排队，直接提交引擎。

**AC-43.2** 批注保存的超时计时（30s）独立于全局队列的任务超时，互不影响。

#### 4.1.2 Spike 实测摘要

引用 02 报告 5 节原始数据与 03 预算表 25-38 行指标定义，遵循「引用 + 摘要表」模式，不复制全文。

2026-09-10 本机四候选对照 spike（`tmp/pdfium-spike/`），合成语料，3 次预热 + 30 次实测，P95 = 升序排序后取 `sorted[floor((n-1)*0.95)]`。硬件：AMD Ryzen 5 5600U / 16GB / Windows 11 Build 26200（02 报告 2 节，与 03 预算表硬件基线一致）。

| 场景 | PDFiumCore 154.0.8035 | PDFtoImage 5.4.0 基线 | 差距 | 预算（03 指标） |
|------|----------------------|----------------------|------|----------------|
| 渲染 P95 96dpi（mixed100 第 10 页） | **3.98 ms** | 13.45 ms | 3.4x | < 200 ms（#1） |
| 渲染 P95 150dpi | **6.52 ms** | 14.33 ms | 2.2x | < 200 ms（#2） |
| 冷启动（text1000 加载 + 首页渲染） | **2.84 ms** | 159.15 ms | 56x | < 3 s（#3，注：此为 binding 层冷启动，非应用层） |
| 并发搜索延迟（渲染并行文本操作） | **0.18 ms** | -- | -- | < 1 s 含锁等待（#4） |
| 全文搜索 P95（cjk500，500 命中） | **55.86 ms** | n/a（无 API） | -- | < 500 ms（#5） |

根因分析（02 报告 8 节）：PDFtoImage 无状态逐页调用，`GetPageSize` 一次 = 一次全量解析，一次渲染 = 2 次全量解析，且整文件读入内存（打开瞬时峰值 2x 文件大小）。持久句柄消除重复解析，是 56x 冷启动差距与 3.4x 渲染差距的来源。渲染性能不是区分维度（四家全部远低于 200 ms 预算），核心收益在冷启动与 API 覆盖。

#### 4.1.3 持久句柄生命周期

```
打开文档: FPDF_LoadDocument(path, password)
  -> 页尺寸一次解析全局缓存
       （遍历一次 FPDF_GetPageSizeByIndex，后续读缓存字典）
  -> 页尺寸缓存存入 Dictionary<int pageIndex, (double width, double height)>
  -> 缓存生命周期 = 文档句柄生命周期

渲染页面（后台线程，持全局锁）:
  -> FPDF_LoadPage(doc, pageIndex)
  -> FPDFBitmap_Create(w, h)
  -> FPDF_RenderPageBitmap(bitmap, page, 0, 0, w, h, 0, FPDF_ANNOT | FPDF_PRINTING)
  -> 位图数据拷贝到 WriteableBitmap（UI 线程显示用）
  -> FPDFBitmap_Destroy / FPDF_ClosePage

关闭文档:
  -> 清除页尺寸缓存
  -> 清除 LRU 位图缓存中该文档的条目
  -> FPDF_CloseDocument(doc)
```

#### 4.1.4 PDFium 全局单锁【R12】

PDFium 全部 API 非线程安全（fpdfview.h 明确声明），并发调用导致原生崩溃。封装层须实现全局 `object` 锁，所有 `FPDF_*` 调用一律包在 `lock` 内，包括但不限于：

- 页尺寸查询（`FPDF_GetPageSizeByIndex`）
- 页面加载/关闭（`FPDF_LoadPage` / `FPDF_ClosePage`）
- 渲染（`FPDF_RenderPageBitmap`）
- 文本操作（`FPDFText_LoadPage` / `FPDFText_GetText` / `FPDFText_FindStart` 等）
- 注释操作（`FPDFPage_CreateAnnot` / `FPDFAnnot_SetRect` 等）
- 保存（`FPDF_SaveWithVersion`）

spike 阻塞比 1.24（并发比串行慢 24%），锁开销可接受（02 报告 6.1 节）。参考实现：DtronixPdf dispatcher thread 串行化模式（阻塞比 0.98）或 Docnet 全局静态锁（DocLib.cs:13-22）。

#### 4.1.5 后台线程渲染

渲染操作不在 UI 线程执行。后台线程池消费渲染任务队列，渲染完成后通过 `Dispatcher.Invoke` 回写 `WriteableBitmap`。UI 线程仅负责显示已渲染的位图，不阻塞。线程安全由全局单锁保证（4.1.4 节）。

#### 4.1.6 页面 LRU 缓存【R9】

- **字节预算**：**<= 256MB**（需求总结 94 行），按渲染位图实际字节数计。
- **LRU 策略**：最近访问的页面驻留，超出预算时淘汰最久未访问的位图。
- **页面尺寸缓存**（页宽高元组）独立于位图缓存，常驻内存，不计入 256MB 预算。
- **验证方法**：256MB 预算属产品层实现（02 报告 6.6 节标注 "spike 未测，非绑定层职责"），spike 未覆盖。实施期需用 working-set 差值法验证（03 预算表指标 #8、#9：500MB PDF working-set 差值 <= 1.2x 文件大小；256MB 缓存下可驻页数 >= 50 页）。

#### 4.1.7 超纹理分块渲染与缩放限幅【R9】

约束：WPF `WriteableBitmap` 上限 4096x4096 像素。缩放 400% x 150 DPI = 5052px，超出上限（notepad 约束记录）。

应对策略：

| 场景 | 策略 | 说明 |
|------|------|------|
| 缩放后尺寸 <= 4096px | 直接渲染 | 正常路径 |
| 缩放后尺寸 > 4096px | 缩放限幅 | 按比例缩放到 4096px 以内，鼠标悬停时重渲染高分辨率区域 |
| 巨页（> 4096px 原始尺寸） | 分块渲染 | 将位图切分为 <= 4096px 的子块，拼接显示 |

巨页探针验证：hugepage 10000x10000pt，PDFiumCore 自动限幅到 4096x4096px（02 报告附 6.6 节健壮性附测）。

#### 4.1.8 虚拟化容器

使用 WPF 虚拟化面板（`VirtualizingStackPanel` 或自定义虚拟化容器）承载页面位图。仅渲染可视区域及预加载缓冲区内的页面，其余页面持有页尺寸缓存但不持有位图。滚动时按需触发后台渲染任务。

虚拟化与 LRU 缓存的交互：可视区域外的页面位图在 LRU 淘汰后释放，再次滚动到时重新渲染（命中页尺寸缓存，渲染耗时 3.98ms/6.52ms）。

#### 4.1.9 现状缺陷对照

| 现状（PdfPreviewDocument / PDFtoImage 5.4.0） | 改进后（PDFiumCore 154.0.8035） |
|----------------------------------------------|-------------------------------|
| 无状态逐页调用，每次渲染重解析整个 PDF | 持久句柄，页尺寸一次解析全局缓存 |
| 同步阻塞 UI 线程 | 后台线程渲染，UI 线程仅显示 |
| 无缓存 | 页面 LRU 缓存（<= 256MB 字节预算） |
| 整文件读入内存（峰值 2x 文件大小） | 句柄化加载，native 内存 working-set 受控 |
| 不支持文本提取/搜索/注释 | FPDFText_* + FPDFAnnot_* 全栈 |

### 4.2 文本层同栈

#### 4.2.1 API 面

文本层与渲染共用同一持久文档句柄（PDFiumCore），通过 `FPDFText_*` 系列 API 实现。spike 验证：CJK 提取正确率 100%，单页耗时 0.15ms（02 报告 6.2 节）。

| 功能 | API | 说明 |
|------|-----|------|
| 加载文本页 | `FPDFText_LoadPage(page)` | 每页一个 text_page 句柄，需在全局锁内调用 |
| 文本提取 | `FPDFText_GetText(text_page, start, count)` | 返回 UTF-16 字符串；输出缓冲 CppSharp 封装正常 |
| 命中测试 | `FPDFText_FindStart` / `FindNext` / `GetSchResultIndex` / `GetSchCount` | 原生搜索（02 报告 6.3 节）；FindNext 返回值语义见 W2 |
| 矩形获取 | `FPDFText_GetCharBox` / `FPDFText_CountRects` | 用于框选与批注定位 |
| 释放文本页 | `FPDFText_ClosePage(text_page)` | 与页面关闭配对 |

#### 4.2.2 坐标复用 PdfCoordinateMapper

复用现有 `PdfCoordinateMapper`，无需新建坐标换算层。该映射器已覆盖：

- 可见旋转页（/Rotate 属性）
- 左上原点坐标系
- pt（点）单位

与 engine.py `area()` 坐标系一致（需求总结 95 行已核实），文本层返回的矩形坐标可直接用于批注定位与框选，无需额外换算。

坐标流向：

```
PDFium FPDFText_GetCharBox -> pt 坐标
  -> PdfCoordinateMapper（旋转校正，左上原点）
    -> region-selection Canvas 像素坐标（渲染栈提供 DPI 换算）
    -> 批注注释坐标（写回 PDF 时反向换算）
```

#### 4.2.3 搜索设计约束

- 搜索 flags=0 默认大小写不敏感（02 报告 6.3 节注记）。
- R13 的 CJK 搜索启发式需在此语义上设计：先用原生 `FPDFText_FindStart` 快速定位，再做客户端二次过滤（如需要大小写敏感）。
- 扫描件无文本层：搜索指标天然不适用（03 预算表注记），需在 UI 层禁用搜索并引导"去 OCR"。

#### 4.3.2 超时与失败处理

- **30s 超时**：由 WPF 侧计时（引擎无内部超时，02 报告关键事实），超时转失败状态。
- **失败重试**：用户手动触发重试，不自动重试。
- **savepill 三态**：未保存 / 保存中 / 已保存（决策 8）。
- **冲突弹窗**：保存前 size/mtime 不一致时弹对话框，用户选择覆盖或取消。

#### 4.3.3 红线：密码持久化禁令

密码绝不进入以下三处持久化存储：

1. **阅读状态**（reading-state/ 目录下的 JSON）——存储最后页码、缩放、滚动偏移，不含密码。
2. **最近列表**（最近打开的文件记录）——存储路径、打开时间、文件大小，不含密码。
3. **会话恢复**（session.json）——存储标签集合、窗口状态，不含密码。

会话密码驻留为 net-new（标签内存会话），解锁一次后续免密，仅存活于进程内存，进程退出即清除。

### 4.4 引擎桥接契约

#### 4.4.1 通信协议

| 方向 | 格式 | 用途 |
|------|------|------|
| WPF -> 引擎（stdin） | 单行 JSON | 请求参数（操作类型、文件路径、选项） |
| 引擎 -> WPF（stdout） | 单行 JSON | 结果返回（成功/失败、输出路径） |
| 引擎 -> WPF（stderr） | 文本流 | 进度百分比、诊断信息 |

#### 4.4.2 四要素

| # | 要素 | 说明 |
|---|------|------|
| 1 | 一进程一请求 | 每次操作启动独立子进程，stdin/stdout 单行 JSON，stderr 进度 |
| 2 | 取消 = taskkill 子进程树 | WPF 侧调用 `taskkill /T /PID` 终止整个进程树 |
| 3 | 密码逐请求 `options.password` | 密码仅在当前请求中传递，不缓存到引擎进程 |
| 4 | 无内部超时 | pure PyMuPDF 操作无内部超时（02 报告关键事实），30s 超时由 WPF 侧计时（批注保存场景） |

#### 4.4.3 会话密码驻留 [net-new]

- **实现方式**：标签内存会话，在 WPF 侧维护一个 `Dictionary<string, string>`（路径 -> 密码），解锁一次后续免密（解锁 UI 见【ST-04】）。

- **加密保存参数**：引擎 save_pdf 现强制 `PDF_ENCRYPT_NONE`，需新增加密保存参数 [net-new]，接收 `options.password` 并保留原文件加密方式（决策 19）。

### 4.6 标签宿主改造【D16】

#### 4.6.1 ToolPageHost -> 标签宿主

`MainWindow` 的 `ToolPageHost`（ContentControl）改造为标签页宿主（TabControl 方向）。每个标签承载一个独立页面实例。参考 01 映射表 17-50 行的通道分布：起始页 6 / 右抽屉 2 / 向导 21 / 临时标签 3 = 32 工具。

#### 4.6.2 每标签页面实例缓存

**现状缺陷**（需求总结 99 行）：registry 每次重建会丢临时标签的工具状态。例如：用户在裁剪标签中框选了区域，切换到其他标签再切回来，框选状态丢失。

**改造方案**：

- 每个标签持有一个页面实例缓存（`Dictionary<TabId, PageInstance>`）。
- 切换标签时复用已缓存的实例，不重建。
- 关闭标签时释放实例与关联的位图缓存（触发 LRU 缓存清理）。
- 复杂编辑工具（编辑/表单/裁剪）以临时标签承载（决策 16），每个临时标签有独立的页面实例。

#### 4.6.3 文档上下文传递

文档上下文传文件走 registry 重载/交接服务 + `AddFiles([path])`（需求总结 99 行，API 已存在于 01 映射表通道承载中）。流程：

  -> 已有：激活现有标签
  -> 无：创建新标签 -> AddFiles([path]) -> 加载渲染
```

### 已知封装注意点

引用 02 报告 7.5 节与 notepad（`.omo/notepads/pdf-reader-prd-prep/learnings.md`），PDFiumCore 封送三条必须在封装层一次性处理：

### W1. WCHAR 字符串封送

**问题**：公开 API 的 `FPDF_WCHAR*` 输入参数（CppSharp 自动生成）封送为空缓冲。实测 `FPDFText_FindStart` 传任何词都"命中" index 0（02 报告 7.5 节第 3 条，notepad "PDFiumCore 154 CppSharp 绑定的坑"）。

**解法**：对 pdfium.dll 直接 `DllImport`（标准 C 导出名 `FPDFText_FindStart` 等）+ `fixed` 指针绕过 CppSharp 封装。spike 已验证可行（02 报告 11.3 节 WCHAR 封送绕过代码片段）。

**受影响的 API 列表**：
- `FPDFText_FindStart`（搜索入口）
- `FPDFAnnot_SetStringValue`（注释文本设置）
- `FPDFAnnot_GetFormField*`（表单字段读取系列）
- `FORM_ReplaceSelection`（表单写入键盘模拟路径）

**不受影响的 API**：输出缓冲（`FPDFText_GetText`）公开 API 反而正常，无需绕过。

### W2. FPDFText_FindNext 返回值语义

**问题**：本 build 的 `FPDFText_FindNext` 返回 1/0（命中/无），不是文档写的 index/-1（02 报告 7.5 节第 5 条，notepad）。

**正确用法**：
- **命中位置**用 `FPDFText_GetSchResultIndex`（实测 46 = 匹配起点）
- **长度**用 `FPDFText_GetSchCount`（实测 10 = len("SECRET-123")）

**封装层处理**：搜索封装须用 `FindNext` 仅判断有无（1/0），位置和长度从 `GetSchResultIndex` / `GetSchCount` 获取。

### W3. FPDF_FORMFILLINFO 委托保活

**问题**：`FPDF_FORMFILLINFO` 回调委托不被 CppSharp 持根。native 调用已 GC 的委托导致进程致命崩溃："callback on collected delegate"（02 报告 7.5 节第 4 条，notepad）。

**解法**：所有 no-op 委托（`FFI_FormFill` 系列回调）存静态列表保活，生命周期与 `InitFormFillEnvironment` 到 `ExitFormFillEnvironment` 一致。`FPDF_FORMFILLINFO` 需 `Version=1` + 全部回调 no-op 委托（02 报告 6.6 节表单 API 验证）。

**关键约束**：pdfium 持有该结构指针至 `ExitFormFillEnvironment`，保活列表不得提前释放。

### 5.2 内存约束

**现状问题**：`PdfPreviewDocument`（PDFtoImage 5.4.0）打开文档瞬时峰值为 **2× 文件大小**（全文件读入内存）。每次渲染调用 `GetPageSize` + `ToImage`，两次全量重解析，无页尺寸缓存、无持久句柄、无 LRU 淘汰。这是当前版本最大的内存隐患，也是决策 18（替换为 PDFiumCore 持久句柄绑定）的核心驱动因素。spike 基线对比：PDFtoImage 冷启动 159ms vs PDFiumCore 2.84ms（约 56 倍改善），渲染 96dpi 13.45ms vs 3.98ms（3.4 倍改善）。根因：PDFtoImage 每页两次全量解析。

**缓解措施**（已裁决，技术约束写入需求总结 :94）：

1. **持久句柄替换**：替换为 PDFiumCore 154.0.8035 持久句柄绑定（决策 18），消除每页全量重解析。页尺寸一次解析全局缓存，后续渲染复用缓存值。spike 验证：冷启动从 159ms（PDFtoImage）降至 2.84ms（PDFiumCore），约 56 倍改善。持久句柄在文档关闭时显式释放，避免 native 内存泄漏。
2. **字节预算 LRU**：渲染服务设字节预算 **≤ 256MB**（LRU 缓存），超出自动淘汰最久未用页的渲染位图。缓存命中率目标 ≥ 50 页同时驻留（B9）。LRU 淘汰策略在内存压力下保证工作集可控，避免无限增长。缓存键为页号 + DPI + 缩放比的组合，不同缩放级别独立缓存。
3. **超纹理限幅**：400% × 150 DPI = 5052px 超 4096px 纹理上限。单页渲染位图可能超出 GPU 纹理尺寸限制，采用分块渲染或缩放限幅，防止单页内存暴涨或渲染失败。分块渲染将超大页拆分为多个 4096px 子区域分别渲染后拼接。
4. **内存验证**：文档加载内存（B8）目标 ≤ 1.2× 文件大小，用 working-set 差值法验证。native 内存（PDFium 句柄 + 缓存）对 .NET GC 不可见，`Environment.WorkingSet` 差值是唯一可靠手段。打开前后各采样 5 次取均值，排除 GC 干扰。500MB 扫描件 PDF 的目标增量为 ≤ 600MB。
5. **全局单锁**：PDFium 所有 API 非线程安全（fpdfview.h 明确声明），并发调用 = 原生崩溃。渲染、文本提取、注释操作共享全局单锁（R12）。blocking ratio 实测 1.24（并发比串行慢 24%，开销可控），不构成瓶颈。锁粒度为文档级，不同文档可并行操作。

### 5.3 安全约束

安全约束沿袭 AGENTS.md 安全约定，在阅读器场景的具体落实如下。密码管理是核心安全边界：密码仅通过 stdin 逐请求传递，不进入任何持久化路径；会话密码驻留为内存标签会话，退出即清除。文档内容和网页来源视为不可信输入，Python 子进程不信任文档内容。

安全设计原则：最小权限、最小暴露、最小持久化。密码在内存中以字符串形式存在（无法在 .NET 中真正"清零"），但通过退出即清除标签会话来限制暴露窗口。文档解析使用 PDFium 沙箱（子进程隔离），不信任文档内容。

| 约束 | 要求 | 来源 |
|------|------|------|
| 密码仅 stdin | 密码经 `options.password` 逐请求传递，仅存在于进程内存，不进入命令行参数、日志、历史记录或会话恢复持久化 | AGENTS.md + 决策 25 |
| 密码不落盘 | 会话密码驻留为内存标签会话（解锁一次后续免密），退出即清除；不写入 `session.json` 或任何持久文件 | 决策 8 |
| 文档与网页是不可信输入 | 沿袭 AGENTS.md 安全约定；Python 子进程不信任文档内容；URL 转 PDF 联网获取页面、脚本和资源，界面与说明必须明示 | AGENTS.md |
| Redaction 用真删 | 永久遮盖（redact）必须应用真正的 redaction 并验证输出，不能把裁剪当作脱敏，不能把黑色覆盖图形当作永久删除 | AGENTS.md |
| 加密文档批注保存 | 加密文档传 password 并保留加密（引擎 `save_pdf` 需新增加密保存参数，当前强制 `PDF_ENCRYPT_NONE`） | 决策 17 |
| 处理器 stdout 约束 | 处理器 stdout 只输出约定 JSON；进度和诊断走 stderr；不输出文档正文或密码 | AGENTS.md |
| 外部命令安全 | 外部命令使用参数数组，保留超时和取消子进程能力，不拼接用户输入执行 shell | AGENTS.md |

**安全约束实施要点**：
- 密码管理：实现时须确保密码字符串不进入任何 `Debug.WriteLine`、日志框架或异常消息。
- 不可信输入：PDF 解析使用 PDFium 沙箱（子进程隔离），不信任文档内容；URL 转 PDF 联网获取页面，界面须明示"正在联网"。
- Redaction 验证：永久遮盖后须验证输出 PDF 中被遮盖内容不可恢复（不能仅视觉覆盖）。

### 5.5 可靠性

可靠性约束涵盖数据持久化、崩溃恢复和运行时保护三个方面。批注保存是可靠性核心路径：必须保证原子写入、冲突检测和超时保护。会话恢复确保异常退出后用户可继续工作。单实例互斥防止多实例并发修改同一文件。

可靠性设计原则：宁可失败显式（提示用户重试），不可失败静默（数据丢失或状态不一致）。所有持久化操作失败时提示用户，不自动重试（避免无限循环）。会话恢复失败时回退到空状态，不崩溃。

1. **原子写**：批注保存采用临时文件 → `os.replace` → `fsync` 就地写回（决策 17）。写入中途崩溃不损坏原文档；临时文件在同一文件系统目录创建，`os.replace` 为 POSIX 原子操作，保证文件内容要么完整更新、要么保持原样。
2. **保存前冲突检测**：打开文档后记录 size/mtime，保存前重新检测。若外部修改（如其他应用编辑同一文件）导致冲突，弹对话框让用户选择覆盖或取消（R10）。防止静默覆盖用户在其他工具中的修改。
3. **崩溃后会话恢复**：退出时持久化标签集合、窗口尺寸/位置/最大化态、左栏宽度与面板选择至 `%APPDATA%\AIPDF\session.json`，启动时恢复（决策 22，沿袭 `WorkflowPresetStore` 模式：schema 版本、UTF-8 no-BOM、文件名消毒、密码剔除）。应用异常退出后重新启动，用户可从上次状态继续。
4. **单实例互斥**：二次启动唤起已有实例并传文件路径开新标签，防止多实例并发修改同一文件（决策 21 连带必须项，文件关联的前置条件）。通过命名互斥体实现。
5. **引擎看门狗**：N 秒无 stderr 提示可取消（R22），具体阈值 PRD 待定。取消机制为 `taskkill` 子进程树。防止引擎挂起导致 UI 无限等待。
6. **批注保存超时**：30 秒超时转失败（决策 25），防止引擎挂起阻塞 UI。超时后提示用户重试或取消。
7. **取消支持**：所有引擎操作支持中途取消（taskkill 子进程树），无内部超时（批注保存的 30s 由 WPF 侧计时）。

### 7.1 性能预算验收
